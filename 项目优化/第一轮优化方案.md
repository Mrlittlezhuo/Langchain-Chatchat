# 第一轮优化方案：最小用户与聊天隔离

## 1. 目标

第一轮只实现一个明确结果：每个登录用户拥有自己的聊天框和历史记录，同时继续共同使用、上传和编辑公共知识库。

典型场景：

- 用户 A 和用户 B 登录同一个 Langchain-Chatchat；
- 两人都能选择公共知识库“无线定位资料”；
- 两人都能向该知识库上传、编辑或删除文件；
- A 只能看到自己的会话和消息；
- B 只能看到自己的会话和消息；
- 两人的提问可以使用同一批知识库内容，但回答分别保存到各自会话。

## 2. 范围边界

| 资源 | 第一轮归属 | 说明 |
|---|---|---|
| 用户账户 | 独立 | 用于识别当前用户 |
| 会话 | 用户私有 | `conversation.owner_id` 是主要隔离边界 |
| 消息 | 用户私有 | 通过所属会话继承，不单独建立复杂 ACL |
| 回答反馈 | 用户私有 | 只能反馈自己会话中的消息 |
| 临时文件对话 | 用户私有 | 临时上传内容属于当前聊天 |
| 聊天图片或附件 | 用户私有 | 不能因为静态 URL 绕过会话边界 |
| 永久知识库 | 全局共享 | 所有登录用户看到同一列表 |
| 知识库文件和向量索引 | 全局共享 | 不增加 owner，不迁移目录 |
| 知识库上传、编辑、删除 | 全局共享写入 | 所有登录用户都可以执行 |
| 模型、工具、MCP | 全局共享 | 保持当前行为 |

## 3. 当前缺口

### 3.1 数据库没有会话所有者

当前 `ConversationModel` 没有 `owner_id`，`MessageModel` 只保存 `conversation_id`。Repository 查询历史时也只按 `conversation_id` 过滤。

影响：知道或构造会话 ID 后，服务端没有用户条件阻止跨用户访问。

### 3.2 WebUI 会话列表主要在 Streamlit 会话内

当前 `ChatBox` 的会话名称、切换和消息展示依赖 `st.session_state`。这会带来两个问题：

1. 登录用户重新打开页面后，无法可靠恢复服务端历史会话；
2. 同一浏览器切换用户时，如果没有彻底清理状态，可能残留上一用户的会话内容。

因此第一轮不只是数据库加字段，还需要增加后端会话列表和消息历史接口，并让 WebUI 从当前用户的后端数据恢复会话。

### 3.3 缺少统一登录身份

FastAPI 路由当前没有统一身份依赖，WebUI 也没有登录入口。服务端无法判断一次聊天请求属于谁。

### 3.4 临时聊天资料需要跟随会话隔离

永久知识库是公共资源，但“文件对话”上传的临时文件和聊天中上传的图片属于私人会话。二者不能因为知识库共享而一并公开。

## 4. 第一轮功能

### 4.1 最小用户体系

实现：

- 首个管理员初始化；
- 管理员创建、禁用、启用用户和重置密码；
- 用户名和密码登录；
- 当前用户查询；
- 退出登录；
- 用户修改自己的密码。

第一轮不实现：

- 公开注册；
- 邮件和短信验证；
- 个人 API Key；
- OIDC/OAuth2；
- 团队、部门和复杂角色；
- 多设备会话管理页面。

### 4.2 会话和消息持久化

增加后端能力：

```text
GET    /conversations
POST   /conversations
GET    /conversations/{conversation_id}
PATCH  /conversations/{conversation_id}
DELETE /conversations/{conversation_id}
GET    /conversations/{conversation_id}/messages
```

行为：

- 创建会话时服务端写入当前用户；
- 列表只返回当前用户会话；
- 获取、重命名和删除同时按会话 ID 与当前用户过滤；
- 消息历史先验证会话属于当前用户；
- 普通聊天、RAG 和 Agent 使用同一套会话归属；
- 流式请求结束后，回答保存到当前用户的会话；
- 回答反馈只能修改当前用户会话中的消息。

### 4.3 WebUI 用户体验

最小页面改动：

- 未登录时显示登录页；
- 侧边栏显示当前用户名和退出入口；
- 会话列表从后端获取；
- 新建、重命名、删除会话调用后端接口；
- 切换会话时从后端加载消息；
- 退出或切换用户时清空 `ChatBox`、`st.session_state` 中的会话、图片、临时文件和模型上下文；
- 公共知识库页面继续显示同一份知识库列表。

### 4.4 公共知识库写入

知识库 CRUD 保持全局共享，不新增 `owner_id` 和用户过滤。

所有已登录用户可以：

- 新建知识库；
- 上传和更新文件；
- 编辑文档片段；
- 从向量库删除文件；
- 删除文件、重建向量库和删除知识库。

为了避免误操作，第一轮只增加最小保护：

- 知识库页面明确标注“公共知识库，修改会影响所有用户”；
- 删除文件、删除知识库和重建向量库前二次确认；
- 请求必须来自已登录用户；
- 记录操作用户名、动作、资源名称、时间和结果的简单审计日志。

审计日志用于追踪公共内容变更，不用于阻止普通用户操作。

### 4.5 临时文件和聊天附件

最小规则：

- 临时文件对话记录 `owner_id`，只能由上传者用于自己的聊天；
- 聊天图片或附件记录上传用户，下载接口验证当前用户；
- 公共知识库中的永久文件仍然共享；
- 如果第一轮无法完成附件鉴权，应临时关闭聊天附件历史恢复，而不是用公开静态地址伪装隔离已经完成。

## 5. 最小数据模型变化

### 5.1 新增 `user`

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `username` | 唯一登录名 |
| `display_name` | 显示名称 |
| `password_hash` | 密码哈希 |
| `role` | `admin` 或 `user` |
| `status` | `active` 或 `disabled` |
| `must_change_password` | 首次登录是否必须修改密码 |
| `create_time`、`update_time` | 时间字段 |

### 5.2 修改 `conversation`

新增：

```text
owner_id    -> user.id，非空并建立索引
update_time -> 用于历史会话排序
```

建议索引：

```text
(owner_id, update_time)
```

### 5.3 `message`

第一轮不必增加 `owner_id`。消息通过 `conversation_id` 关联会话，授权查询必须连接或先验证会话所有者。

应补充 conversation 外键或等效完整性约束，避免孤立消息。

### 5.4 临时聊天资源

用于临时文件对话和聊天附件的记录增加 `owner_id`。永久知识库相关表不修改用户归属。

### 5.5 不修改的公共表

以下表第一轮不增加 owner：

- `knowledge_base`；
- `knowledge_file`；
- `file_doc`；
- 公共知识库向量索引；
- `mcp_connection`；
- `mcp_profile`。

## 6. 授权规则

### 6.1 当前用户来源

服务端从经过验证的登录凭据得到：

```python
class CurrentUser:
    id: str
    username: str
    role: str
```

客户端请求中的 `user_id` 不参与授权。

### 6.2 会话 Repository

禁止仅按 ID 查询：

```python
get_conversation(conversation_id)
filter_message(conversation_id)
```

使用当前用户边界：

```python
get_conversation(current_user.id, conversation_id)
list_conversations(current_user.id)
list_messages(current_user.id, conversation_id)
```

更新和删除同样必须带 `owner_id` 条件。

### 6.3 知识库 Repository

保持当前全局查询方式，不增加当前用户过滤。知识库接口只要求“已经登录”，所有用户得到同样的知识库数据。

### 6.4 响应规则

访问其他用户会话时统一返回 `404`，不暴露该会话是否存在。公共知识库不存在时也按现有资源不存在处理。

## 7. 登录实现取舍

为减少改动，第一轮可采用短期访问令牌：

- 登录成功后 WebUI 把令牌保存在当前 Streamlit 会话中；
- 每个 API 请求携带 Bearer Token；
- Token 包含用户 ID 和过期时间；
- 每次请求仍检查用户是否处于 active 状态；
- 退出时清空 WebUI 令牌和全部聊天状态；
- Token 生命周期保持较短，过期后重新登录。

这种方式省去刷新会话表和复杂设备管理。后续如果需要长时间登录、强制注销和多设备管理，再增加可撤销服务端会话。

## 8. 共享知识库的并发和责任提示

允许所有用户写入公共知识库是明确的产品选择，也意味着：

- 一个用户上传的资料会被所有用户检索；
- 一个用户删除或修改内容会影响所有人的后续回答；
- 同时重建和编辑可能产生冲突；
- 知识库中不应上传个人隐私资料。

第一轮不建立复杂权限，但应至少做到：

1. 危险操作二次确认；
2. 操作审计；
3. 同一知识库重建和写入使用现有锁或最小互斥；
4. 页面明确提示公共影响范围；
5. 不把临时聊天文件误入公共知识库。

## 9. 存量数据迁移

最小迁移步骤：

1. 备份数据库；
2. 创建一个 `legacy-admin` 用户；
3. 给 `conversation` 增加可空 `owner_id`；
4. 将所有旧会话归属 `legacy-admin`；
5. 校验会话数和消息数；
6. 将 `owner_id` 调整为非空；
7. 创建必要索引；
8. 启动新版本并验证历史会话。

不需要：

- 移动知识库目录；
- 重建 FAISS 索引；
- 修改知识库名称；
- 给知识库文件补用户归属；
- 迁移 MCP 配置。

## 10. 测试矩阵

准备 `admin`、`user_a`、`user_b`。

### 登录

- 正确和错误密码；
- 禁用账户；
- 令牌过期；
- 退出后清空当前浏览器聊天状态。

### 会话隔离

- A 和 B 的会话列表不同；
- A 不能通过替换 ID 读取、重命名、删除 B 的会话；
- A 不能读取或反馈 B 的消息；
- 普通聊天、RAG、Agent 和流式请求都写入正确用户会话；
- 同一浏览器先登录 A 再登录 B，不显示 A 的任何历史内容；
- 服务重启后用户仍能恢复自己的历史会话。

### 临时内容

- A 不能使用 B 的临时文件对话 ID；
- A 不能下载 B 的聊天附件；
- 临时内容不会进入公共知识库。

### 公共知识库

- A 新建或上传后，B 可以看到并检索；
- B 编辑后，A 可以看到更新；
- A 和 B 得到相同的公共知识库列表；
- 知识库接口未错误增加 owner 过滤；
- 删除和重建前有公共影响提示和确认；
- 审计记录能够指出操作用户。

## 11. 实施顺序

### 阶段 A：用户身份

1. 增加用户表和迁移；
2. 增加管理员初始化；
3. 增加登录、当前用户、退出、修改密码接口；
4. WebUI 增加登录页和当前用户展示。

### 阶段 B：后端会话隔离

1. conversation 增加 owner；
2. 增加会话 CRUD 和历史接口；
3. 所有聊天链路校验会话所有权；
4. 增加用户 A/B 越权测试。

### 阶段 C：WebUI 历史恢复

1. 会话列表从后端加载；
2. 切换会话加载消息；
3. 新建、重命名、删除走后端；
4. 登出和换用户彻底清理 Streamlit 状态。

### 阶段 D：临时聊天内容

1. 临时文件和附件绑定用户；
2. 下载和使用时验证用户；
3. 与公共知识库文件明确区分。

### 阶段 E：共享知识库回归

1. 所有登录用户保持写权限；
2. 增加公共影响提示、确认和简单审计；
3. 验证没有误加入知识库用户过滤。

## 12. 完成标准

- 每个用户只看到自己的聊天框和历史记录；
- 浏览器换用户不会残留上一用户聊天；
- 修改会话 ID 无法越权；
- 服务重启后仍能恢复当前用户历史；
- 普通聊天、RAG 和 Agent 使用同一隔离规则；
- 临时聊天文件和附件不会跨用户；
- 永久知识库仍由所有登录用户共同查看、上传和编辑；
- 旧知识库和向量索引不迁移、不重建；
- 旧会话归属遗留管理员且数量完整；
- 自动化测试覆盖认证、越权和共享知识库回归。

## 13. 第一轮非目标

- 知识库所有权和用户隔离；
- 团队空间、知识库分享和资源 ACL；
- MCP、模型、工具按用户隔离；
- 普通用户与知识库管理员权限区分；
- 个人 API Key 和外部身份提供器；
- 完整任务队列和大规模部署改造；
- 前端框架替换。
