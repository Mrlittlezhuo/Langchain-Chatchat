## 3. 背景

项目当前主要依赖 `Base.metadata.create_all()` 创建缺失表。该方式不会安全地给已有表增加字段、回填数据或记录迁移版本。后续用户体系需要新增用户表，并给现有 conversation 增加非空 owner；如果没有迁移基线，容易通过删库重建或临时 SQL 造成旧聊天数据丢失。

本任务只建立最小、可测试的数据库迁移能力，不实现用户表、认证、会话 owner 或 WebUI。

## 4. 目标

1. 提供按版本顺序执行、重复运行安全的最小迁移机制；
2. 提供迁移状态查看和显式升级入口；
3. SQLite 执行升级前生成数据库备份，并在失败时保留原库和备份；
4. 使用临时 SQLite 数据库自动验证版本记录、幂等性和数据保留；
5. 不修改、移动或重建知识库文件与向量索引。

## 5. 允许修改范围

- `libs/chatchat-server/chatchat/server/db/` 下新增迁移模块或迁移目录；
- `libs/chatchat-server/chatchat/cli.py`，仅用于注册迁移 CLI；
- `libs/chatchat-server/tests/` 下本任务的迁移测试；
- 为导入迁移模块所必需的相邻 `__init__.py`；

如果实现必须修改 `settings.py`、`startup.py`、知识库迁移模块或依赖声明，先停止并说明原因，由 Codex 决定是否扩大范围。

## 6. 禁止事项

## 7. 设计约束

### 7.1 最小迁移机制

- 使用 SQLAlchemy 已有依赖实现，不引入完整迁移框架；
- 迁移按单调递增版本注册并按顺序执行；
- 使用独立的 schema version 表记录已成功版本；
- 每个版本与版本记录必须处于同一事务；
- 已成功版本不得重复执行；
- 未知的更高数据库版本必须拒绝降级执行并给出清晰错误；
- 迁移核心应接受显式 engine/connection，避免测试绑定全局真实数据库。

### 7.2 SQLite 备份

- 升级前对目标 SQLite 文件创建带时间或唯一标识的备份；
- 备份路径必须明确显示给操作者；
- 内存数据库不要求文件备份；
- 备份失败时不得继续迁移；
- 不覆盖已有备份；
- 测试只使用临时目录。

### 7.3 CLI

在现有 `chatchat` CLI 下提供语义清楚的迁移命令，至少支持：

- 查看当前版本和可用最新版本；
- 显式升级到最新版本；
- 输出备份位置、已执行版本和最终版本；
- 失败时返回非零退出状态并显示可操作错误。

CLI 的具体子命令命名可结合现有 Click 结构决定，但不能与知识库的 `kb`/`init` 语义混淆。

### 7.4 当前版本内容

本任务可以使用一个“只建立版本表”的初始版本验证框架，但不得提前创建用户表或修改 conversation。后续业务 schema 变化由新的 Claude 任务完成。

## 9. 测试要求

至少覆盖：

- 空临时 SQLite 数据库首次升级；
- 连续运行两次，第二次不重复执行；
- 多个模拟版本严格按顺序执行；
- 某版本失败时不记录该版本，业务变更回滚；
- 数据库版本高于代码版本时拒绝运行；
- 文件 SQLite 升级前创建备份，备份内容可读取；
- 备份目标已存在时不覆盖；
- 现有示例 conversation/message 数据在空操作迁移前后数量和值一致；
- CLI status 和 upgrade 的成功、失败退出行为。
