## 3. 背景

项目当前主要依赖 `Base.metadata.create_all()` 创建缺失表。该方式不会安全地给已有表增加字段、回填数据或记录迁移版本。后续用户体系需要新增用户表，并给现有 conversation 增加非空 owner；如果没有迁移基线，容易通过删库重建或临时 SQL 造成旧聊天数据丢失。

本任务只建立最小、可测试的数据库迁移能力，不实现用户表、认证、会话 owner 或 WebUI。

## 4. 目标

1. 提供按版本顺序执行、重复运行安全的最小迁移机制；
2. 提供迁移状态查看和显式升级入口；
3. SQLite 执行升级前生成数据库备份，并在失败时保留原库和备份；
4. 使用临时 SQLite 数据库自动验证版本记录、幂等性和数据保留；
5. 不修改、移动或重建知识库文件与向量索引。

## 7. 设计约束

### 7.1 最小迁移机制

- 使用 SQLAlchemy 已有依赖实现，不引入完整迁移框架；
- 迁移按单调递增版本注册并按顺序执行；
- 使用独立的 schema version 表记录已成功版本；
- 每个版本与版本记录必须处于同一事务；
- 已成功版本不得重复执行；
- 未知的更高数据库版本必须拒绝降级执行并给出清晰错误；
- 迁移核心应接受显式 engine/connection，避免测试绑定全局真实数据库。

### 7.2 SQLite 备份

- 升级前对目标 SQLite 文件创建带时间或唯一标识的备份；
- 备份路径必须明确显示给操作者；
- 内存数据库不要求文件备份；
- 备份失败时不得继续迁移；
- 不覆盖已有备份；
- 测试只使用临时目录。

### 7.3 CLI

在现有 `chatchat` CLI 下提供语义清楚的迁移命令，至少支持：

- 查看当前版本和可用最新版本；
- 显式升级到最新版本；
- 输出备份位置、已执行版本和最终版本；
- 失败时返回非零退出状态并显示可操作错误。

CLI 的具体子命令命名可结合现有 Click 结构决定，但不能与知识库的 `kb`/`init` 语义混淆。

### 7.4 当前版本内容

本任务可以使用一个“只建立版本表”的初始版本验证框架，但不得提前创建用户表或修改 conversation。后续业务 schema 变化由新的 Claude 任务完成。

### 关键设计选择

1. **核心接受显式 `Connection`**：`apply_migrations(registry, conn, ...)` 不绑定全局 engine，测试可指向临时/内存数据库；CLI 层负责从 `Settings` 建 engine。
2. **版本记录表独立于业务表**：`schema_migrations(version, name, applied_at)` 由框架幂等创建（`CREATE TABLE IF NOT EXISTS`），业务 DDL 由各迁移负责。`current_version()`/`ensure_version_table()` 会幂等建表以便“空库”能查询（返回 None）。
3. **每版本独立事务 + 失败即停**：每个迁移在 `conn.begin()` 块内执行升级体并同事务写入版本记录；升级体抛异常时本版本全部变更（含业务 DDL/DML）回滚、不记录该版本，并立即停止后续版本。对连接残留的只读 autobegin 先 `rollback()` 清除再开新事务（SQLAlchemy 2.0 autobegin 兼容）。
4. **单次升级前备份**：`before_upgrade` 回调在**所有迁移执行前调用一次**（非每版本一次），由 CLI 对文件型 SQLite 创建 `{db}.bak-{UTC时间戳}-{4位hex}.db`；备份失败抛 `BackupError`，CLI 中止升级并返回非零。备份内容经只读校验后才视为成功。
5. **降级拒绝**：数据库版本高于代码最新版本时 `pending_migrations` 抛 `MigrationError`，CLI status/upgrade 返回非零并给出可操作错误。
6. **当前版本内容**：v1 仅建立版本记录表，未创建用户表、未修改 conversation（符合 7.4 约束）。
7. **CLI 不隐式建库/重建**：`migrate` 只显式建版本表/改 schema 版本，不调用 `create_tables`/`reset_tables`/知识库迁移；导入 `migrate.cli` 不产生数据库修改（有专门测试）。

### 未完成项与风险

- **未实现**用户表、认证、conversation owner、WebUI（本任务明确排除，由后续任务完成）。
- **风险 1**：`ensure_version_table` 用 `CREATE TABLE IF NOT EXISTS` 幂等建版本表。对已有业务表但无版本表的旧库，首次 `status`/`upgrade` 会补建该表并记为 v0，行为符合预期，但 Codex 需确认“旧库无版本表”的语义是否需额外处理。
- **风险 2**：备份基于 SQLite 文件复制，未用 `VACUUM INTO`/online backup API，极端并发写入下可能产生不一致快照；当前场景（升级前、单进程）风险低。后续若需强一致可改用 `sqlite3.Connection.backup`。
- **风险 3**：`chatchat/cli.py` 顶层导入 `migrate.cli`，而 `migrate.cli` 顶层导入 `chatchat.settings`（无副作用），不产生数据库修改；但若未来 settings 导入引入副作用需复核。
- 测试未覆盖 `before_upgrade` 抛 `BackupError` 时 CLI 中止的完整路径（仅覆盖了备份文件存在性），可在后续任务补强。

## 12. Codex 审查记录

- 审查状态：`approved`
- 主要发现：
  - P1：pysqlite 默认不会在首条 DDL 前主动发送 `BEGIN`，原实现中迁移建表后失败时表结构无法回滚，不满足“迁移内容与版本记录同事务”。
  - P1：直接复制 SQLite 主文件可能遗漏 WAL 中已提交数据；备份文件名二次碰撞时也仍可能覆盖已有文件。
  - P1：`status` 会通过 `current_version()` 创建版本表，属于查询命令隐式改库；无待执行迁移时 `upgrade` 仍会产生多余备份。
  - P2：注册空洞版本失败后错误版本仍留在注册表；CLI 未统一释放 engine，也没有覆盖备份失败和普通迁移异常的可操作输出。
- 补充修改：
  - SQLite 迁移事务显式执行 `BEGIN`，补充首次迁移 DDL 失败时版本表和业务表均回滚的测试。
  - `current_version()` 改为纯查询并校验迁移历史连续性；注册版本先校验后写入；仅在确有待执行迁移时调用升级前备份。
  - 备份改用 SQLite online backup API，原子独占创建目标文件并执行 `integrity_check`，覆盖 WAL 一致性和固定文件名碰撞测试。
  - CLI 补齐资源释放、备份失败/普通异常处理，并保证 `status` 不创建版本表或不存在的数据库文件。
