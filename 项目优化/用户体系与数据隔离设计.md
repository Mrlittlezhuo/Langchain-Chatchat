# 用户体系与聊天隔离设计（最小改动版）

## 1. 设计结论

第一轮只隔离聊天，不隔离知识库。

用户登录后拥有自己的：

- 聊天框和会话列表；
- 历史消息；
- 回答反馈；
- 临时文件对话和聊天附件。

所有登录用户共同拥有并可以编辑：

- 永久知识库；
- 知识库文件；
- 向量索引；
- 模型、工具和 MCP 配置。

因此本设计不再要求知识库、向量库、MCP 和工具增加 `owner_id`，也不迁移它们的存储路径。

## 2. 用户看到的最终行为

```text
用户 A 登录
  -> 只看到 A 的会话 1、会话 2
  -> 可以使用公共知识库 K
  -> 可以上传和编辑 K 的文件

用户 B 登录
  -> 只看到 B 的会话 1、会话 2
  -> 也可以使用公共知识库 K
  -> 也可以上传和编辑 K 的文件
```

A 和 B 的聊天历史完全分开，但公共知识库 K 的变化对两人同时生效。

## 3. 当前代码与目标之间的差距

### 3.1 会话没有用户归属

当前 `ConversationModel` 只有会话 ID、名称、聊天类型和创建时间，没有用户字段：

- `../libs/chatchat-server/chatchat/server/db/models/conversation_model.py`

当前消息只保存 `conversation_id`：

- `../libs/chatchat-server/chatchat/server/db/models/message_model.py`

只使用随机会话 ID 不能构成访问控制。

### 3.2 历史会话没有完整的后端用户列表接口

WebUI 的会话列表和切换主要由 `streamlit_chatbox.ChatBox` 与 `st.session_state` 管理：

- `../libs/chatchat-server/chatchat/webui_pages/dialogue/dialogue.py`

数据库虽然保存了 conversation/message，但当前没有形成“登录用户 -> 会话列表 -> 历史消息”的完整恢复链路。

### 3.3 服务端不知道当前用户

FastAPI 当前直接注册业务 Router，没有统一认证依赖：

- `../libs/chatchat-server/chatchat/server/api_server/server_app.py`

需要一个最小认证上下文为聊天请求提供用户 ID。

### 3.4 知识库的全局结构符合新范围

知识库目前通过全局 `kb_name` 和公共磁盘目录管理。第一轮继续使用这一结构，不把它视为缺陷。

## 4. 最小账户模型

新增 `user` 表：

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | UUID/String(32) | 主键 |
| `username` | String | 唯一登录名 |
| `display_name` | String | 显示名称 |
| `password_hash` | String | 密码哈希 |
| `role` | String | `admin` 或 `user` |
| `status` | String | `active` 或 `disabled` |
| `must_change_password` | Boolean | 初始密码首次登录修改 |
| `create_time` | DateTime | 创建时间 |
| `update_time` | DateTime | 更新时间 |

第一轮不增加 refresh session、API Key、workspace、member 和 ACL 表。

## 5. 最小会话模型变化

### 5.1 `conversation`

新增：

```text
owner_id: user.id，非空、索引
update_time: 用于按最近活动排序
```

建议索引：

```text
INDEX conversation_owner_updated(owner_id, update_time)
```

### 5.2 `message`

保持现有字段，通过 `conversation_id` 继承会话用户边界。

授权读取示意：

```sql
SELECT message.*
FROM message
JOIN conversation ON conversation.id = message.conversation_id
WHERE conversation.id = :conversation_id
  AND conversation.owner_id = :current_user_id;
```

更新回答和提交反馈也必须经过相同边界，不能只按 `message.id` 更新。

### 5.3 `human_message_event`

Agent 人工交互事件通过 `conversation_id` 继承会话所有权。读取和提交事件前验证会话属于当前用户。

### 5.4 临时聊天资源

临时文件知识库、聊天图片或附件属于聊天内容，需要记录 `owner_id`，或通过 conversation 关联用户。

永久知识库文件不增加用户字段。

## 6. 最小认证设计

### 6.1 接口

```text
POST /auth/login
GET  /auth/me
POST /auth/logout
POST /auth/change-password
```

管理员最小接口：

```text
GET   /admin/users
POST  /admin/users
PATCH /admin/users/{user_id}/status
POST  /admin/users/{user_id}/reset-password
```

### 6.2 令牌

第一轮使用短期 Bearer Token，WebUI 保存在当前 Streamlit 会话中：

- 不放在 URL；
- Token 包含用户 ID 和过期时间；
- 每次请求检查用户仍为 active；
- 退出时清空令牌和全部用户聊天状态；
- Token 过期后重新登录。

这避免第一轮增加刷新令牌和多设备会话管理。

### 6.3 服务端当前用户

```python
class CurrentUser:
    id: str
    username: str
    role: str
```

由统一依赖解析。请求体和查询参数中的 `user_id` 永远不能覆盖它。

## 7. 会话 API 设计

### 7.1 列表

```text
GET /conversations
```

只返回：

```text
conversation.owner_id == current_user.id
```

按 `update_time DESC` 排序。

### 7.2 创建

```text
POST /conversations
```

服务端设置 `owner_id=current_user.id`。客户端不能指定 owner。

### 7.3 读取、重命名和删除

```text
GET    /conversations/{id}
PATCH  /conversations/{id}
DELETE /conversations/{id}
```

Repository 查询必须同时包含 `id` 和 `owner_id`。其他用户访问统一返回 404。

### 7.4 历史消息

```text
GET /conversations/{id}/messages
```

先验证会话所有权，再返回消息。建议按创建时间正序返回，页面负责渲染。

### 7.5 Chat Completions

- 请求中的 `conversation_id` 必须属于当前用户；
- 没有 conversation ID 时由服务端为当前用户创建会话；
- 普通对话、RAG 和 Agent 使用同一判断；
- 后台流式任务携带已经验证的用户上下文；
- 保存问题、回答和中间步骤时使用同一个会话；
- 用户不能用自己身份写入其他用户会话。

## 8. WebUI 最小改动

### 8.1 登录状态

- 未登录时只显示登录页；
- 登录后显示当前用户名和退出按钮；
- API 请求统一携带 Token；
- 用户被禁用或 Token 过期时回到登录页。

### 8.2 历史会话

- 页面打开后调用 `/conversations`；
- 选择会话后调用 messages 接口；
- 新建、重命名、删除不再只修改 `ChatBox` 内存；
- 当前会话 ID 以服务端记录为准；
- `ChatBox` 只承担渲染，不充当持久化数据源。

### 8.3 换用户清理

退出时至少清理：

- 当前会话 ID 和会话名称；
- ChatBox history/context；
- 上传图片；
- 临时文件对话 ID；
- 当前 Agent 状态；
- 当前模型 System Message 等可能包含上一用户内容的状态。

如果使用 Streamlit cache，缓存键必须包含用户 ID，或者不缓存用户私有聊天数据。

## 9. 公共知识库规则

### 9.1 保持全局共享

以下行为不增加 owner 过滤：

- 列出知识库；
- 创建知识库；
- 上传、下载和编辑永久知识文件；
- 检索知识库；
- 更新、删除文件；
- 重建和删除知识库。

所有登录用户的结果一致。

### 9.2 最小安全提示

页面显示：

> 当前为公共知识库。上传、编辑、删除和重建操作会影响所有用户。

以下操作二次确认：

- 删除永久文件；
- 从向量库删除；
- 重建向量库；
- 删除知识库。

### 9.3 简单审计

为了在共享写入发生误操作时找到原因，记录：

```text
username
action
resource_type
resource_name
result
create_time
```

审计不改变权限；普通用户仍然可以执行公共知识库操作。

## 10. 不需要做的改动

第一轮明确不做：

- `knowledge_base.owner_id`；
- `knowledge_file.owner_id`；
- `file_doc.owner_id`；
- 用户独立知识库目录；
- 用户独立 FAISS 索引；
- 远程向量库 metadata 用户过滤；
- `mcp_connection.owner_id`；
- 工具用户 ACL；
- 知识库分享表；
- workspace/team 模型。

这也是本版相对原设计减少的主要工作量。

## 11. 存量数据迁移

1. 备份数据库；
2. 创建 `legacy-admin`；
3. 新增用户表；
4. conversation 增加可空 owner；
5. 全部旧会话归属 `legacy-admin`；
6. 校验会话和消息数量；
7. owner 改为非空并增加索引；
8. 验证旧聊天恢复。

公共知识库数据库、磁盘文件和向量索引保持原样，不执行知识库重建。

## 12. 测试重点

### 12.1 必测隔离

- A/B 会话列表互不可见；
- A 不能读取、重命名、删除 B 的会话；
- A 不能更新或反馈 B 的消息；
- 直接替换 conversation/message ID 不能越权；
- SSE 流式和 Agent 后台任务保存到正确会话；
- 浏览器从 A 切换到 B 后没有 A 的残留内容；
- 服务重启后历史仍可恢复。

### 12.2 必测共享

- A 创建知识库后 B 立即可见；
- A 上传文件后 B 可以检索；
- B 编辑知识片段后 A 可以看到更新；
- 两个用户可以操作同一知识库；
- 公共知识库接口没有被误加 owner 条件；
- 危险操作显示公共影响确认；
- 审计记录包含实际操作用户。

### 12.3 临时文件边界

- A 不能访问 B 的临时文件对话；
- A 不能下载 B 的聊天附件；
- 永久知识库文件仍然对 A/B 共享。

## 13. 最小完成定义

- 登录后才能进入应用；
- 每个用户看到自己的会话列表和历史消息；
- 所有会话读取、更新和删除都有用户条件；
- 换用户时 Streamlit 状态完全清理；
- 普通聊天、RAG、Agent 和临时文件对话遵循同一聊天隔离；
- 公共知识库仍可由所有登录用户上传和编辑；
- 旧知识库无需迁移或重建；
- 认证、越权、状态清理和公共知识库共享都有自动化测试。
