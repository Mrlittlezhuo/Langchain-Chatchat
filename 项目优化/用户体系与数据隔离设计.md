# 用户体系与数据隔离设计

## 1. 设计目标

本设计首先解决“当前聊天和知识库没有用户隔离”的问题。第一轮采用简单、明确的私有资源模型：

- 一个普通用户只能访问自己的资源；
- 管理员负责账户和系统配置管理；
- 默认不支持用户之间分享资源；
- 所有授权判断都在服务端执行；
- 数据库、磁盘文件、向量检索、媒体下载和工具执行使用同一个身份边界。

团队空间和共享知识库不在第一轮实现，但数据库主键和服务接口不应阻碍后续增加共享关系。

## 2. 当前风险证据

### 2.1 API 没有统一认证

当前应用直接注册 Chat、Knowledge Base、Tool、OpenAI、Server 和 MCP Router，没有统一的认证依赖：

- `../libs/chatchat-server/chatchat/server/api_server/server_app.py`

一旦监听地址可被其他设备访问，业务接口就处于同一信任域。

### 2.2 会话和消息没有所有者

`ConversationModel` 只有 `id`、`name`、`chat_type` 和时间；`MessageModel` 只通过 `conversation_id` 关联会话：

- `../libs/chatchat-server/chatchat/server/db/models/conversation_model.py`
- `../libs/chatchat-server/chatchat/server/db/models/message_model.py`

当前仓库查询会话消息时只按 `conversation_id` 过滤，随机 ID 不能代替权限控制。

### 2.3 知识库依赖全局名称

`KnowledgeBaseModel` 没有所有者，知识文件与向量文档通过 `kb_name` 关联：

- `../libs/chatchat-server/chatchat/server/db/models/knowledge_base_model.py`
- `../libs/chatchat-server/chatchat/server/db/models/knowledge_file_model.py`

这会产生三个问题：

1. 不同用户不能安全使用同名知识库；
2. 磁盘目录、数据库和向量库很难使用同一个稳定边界；
3. API 如果只接收 `knowledge_base_name`，无法证明资源属于当前用户。

### 2.4 MCP 配置和凭据是全局资源

MCP 的 `server_name` 当前全局唯一，`env` 和 `config` 直接保存在 JSON 字段中，模型本身没有用户归属：

- `../libs/chatchat-server/chatchat/server/db/models/mcp_connection_model.py`

这意味着多人使用时存在连接器名称冲突、配置泄露和凭据误用风险。

### 2.5 媒体目录绕过业务鉴权

当前 `/media` 使用 FastAPI `StaticFiles` 直接挂载。静态服务器不会自动执行知识库、会话或用户所有权检查，因此不能继续用于私有用户文件的直接下载。

## 3. 身份与角色模型

### 3.1 第一轮角色

| 角色 | 权限 |
|---|---|
| `admin` | 创建、禁用、启用用户，重置密码，查看系统状态和审计事件；拥有自己的私有业务资源 |
| `user` | 管理自己的会话、知识库、文件、API Key、MCP 连接器和个人设置 |

第一轮不增加 viewer、editor、团队管理员等复杂角色。

### 3.2 账户策略

- 私有部署默认关闭公开注册；
- 首个管理员通过 CLI 初始化，初始密码只显示一次并要求首次登录修改；
- 用户名规范化后唯一，显示名称可以重复；
- 密码使用现代密码哈希算法并配置合理参数，不保存或记录明文；
- 管理员重置密码后，用户已有登录会话和 API Key 按策略失效；
- 禁用账户立即拒绝新请求；
- 删除账户第一轮采用停用或软删除，数据删除使用单独的、可审计的流程。

### 3.3 认证方式

| 使用方 | 建议方式 |
|---|---|
| Streamlit WebUI | 登录接口取得短期访问令牌和可撤销刷新会话；令牌不得进入 URL |
| Python SDK、自动化脚本 | 用户创建的个人 API Key，通过 Bearer Header 发送 |
| 管理脚本 | 管理员 API Key 或本机受控 CLI |
| 后续企业接入 | OIDC/OAuth2，作为后续认证提供器，不进入第一轮 |

部署配置建议支持：

```text
AUTH_MODE=local      # 仅本机兼容模式，映射到固定系统用户
AUTH_MODE=password   # 多用户密码认证，网络部署默认
```

`local` 模式不是匿名多用户模式。它必须映射到一个固定的本地用户，并且只能在明确的本地受信任部署中使用。

## 4. 建议数据模型

### 4.1 新增表

#### `user`

| 字段 | 说明 |
|---|---|
| `id` | UUID，主键 |
| `username` | 规范化用户名，唯一 |
| `display_name` | 页面显示名称 |
| `email` | 可选，第一轮不承担邮件验证 |
| `password_hash` | 密码哈希 |
| `role` | `admin` 或 `user` |
| `status` | `active`、`disabled`、`deleted` |
| `must_change_password` | 是否必须修改初始密码 |
| `password_changed_at` | 密码修改时间，用于令牌失效 |
| `created_at`、`updated_at`、`last_login_at` | 审计字段 |

#### `auth_session`

| 字段 | 说明 |
|---|---|
| `id` | 会话 UUID |
| `user_id` | 用户 ID |
| `refresh_token_hash` | 只保存刷新凭据哈希 |
| `expires_at` | 到期时间 |
| `revoked_at` | 撤销时间 |
| `created_ip`、`user_agent` | 可选的安全审计信息，需控制保留周期 |

#### `api_key`

| 字段 | 说明 |
|---|---|
| `id` | API Key ID |
| `user_id` | 所属用户 |
| `name` | 用户可识别名称 |
| `key_prefix` | 页面用于识别的非敏感前缀 |
| `key_hash` | Key 哈希，不保存完整 Key |
| `last_used_at`、`expires_at`、`revoked_at` | 生命周期字段 |

#### `audit_log`

| 字段 | 说明 |
|---|---|
| `id` | 审计事件 ID |
| `actor_user_id` | 操作用户，系统任务可以为空 |
| `action` | 如 `user.disable`、`kb.delete`、`tool.confirm` |
| `resource_type`、`resource_id` | 操作对象 |
| `result` | `success` 或 `denied` 等 |
| `trace_id` | 与应用日志关联 |
| `metadata` | 严格脱敏的补充信息 |
| `created_at` | 发生时间 |

#### `ingestion_job`

记录当前用户文件入库过程，字段详见第一轮优化方案。任务表必须包含 `user_id` 和 `knowledge_base_id`。

### 4.2 修改现有表

| 表 | 修改建议 |
|---|---|
| `conversation` | 增加非空 `owner_id`、`updated_at`、可选 `deleted_at`；索引 `(owner_id, create_time)` |
| `message` | 继续归属于会话；可增加 `owner_id` 作为防御性隔离和高效索引；增加会话外键 |
| `knowledge_base` | 增加稳定 UUID `kb_id` 和非空 `owner_id`；名称唯一约束改为 `(owner_id, normalized_name)` |
| `knowledge_file` | 使用 `knowledge_base_id` 外键，不再仅依赖 `kb_name`；增加稳定 `file_id` 和存储键 |
| `file_doc` | 使用 `knowledge_base_id`、`file_id`；保留向量文档 ID；必要时增加 `owner_id` 便于过滤校验 |
| `human_message_event` | 通过 conversation 归属用户；查询必须验证 conversation 所有权 |
| `mcp_connection` | 增加 `owner_id`；唯一约束改为 `(owner_id, server_name)`；敏感配置加密存储 |
| `mcp_profile` | 增加唯一 `owner_id`，实现每用户一份个人配置 |

SQLAlchemy 的 JSON 默认值应同时从 `default={}`、`default=[]` 改为可调用默认值，避免共享可变对象。

### 4.3 为什么知识库需要稳定 ID

用户可以重命名知识库，但磁盘目录和向量集合不应随显示名变化。建议：

```text
显示名称：无线定位资料
kb_id：2de39c2f...
存储路径：data/users/{user_id}/knowledge_bases/{kb_id}/
```

所有内部 API、数据库关系和文件路径使用 `kb_id`；显示名称只用于页面展示。兼容旧 API 时可以临时接受名称，但必须在当前用户范围内解析，不能全局查找。

## 5. 服务端授权架构

### 5.1 认证上下文

统一依赖返回：

```python
class Principal:
    user_id: str
    username: str
    role: str
    auth_method: str
    session_id: str | None
```

业务路由使用类似以下形式：

```python
current = Depends(get_current_principal)
```

任何路由都不得把请求体中的 `user_id` 赋给 `current.user_id`。

### 5.2 Repository 约束

所有资源查询都必须包含用户范围。禁止以下模式：

```python
get_message_by_id(message_id)
get_knowledge_base_by_name(kb_name)
filter_message(conversation_id)
```

建议改为：

```python
get_message(user_id, message_id)
get_knowledge_base(user_id, kb_id)
list_messages(user_id, conversation_id)
```

Repository 层仍需过滤 `owner_id`，不能只依赖路由层已经检查过。更新和删除使用带用户范围的单条 SQL 条件，避免“先查后改”之间出现边界遗漏。

### 5.3 返回 404 还是 403

对于用户请求其他人的具体资源，默认返回统一的 `404 RESOURCE_NOT_FOUND`，避免泄露该 ID 是否存在。对于明确的系统管理功能，可以返回 `403 FORBIDDEN`。

### 5.4 路由分组

```text
/auth/login
/auth/refresh
/auth/logout
/auth/me
/auth/password
/api-keys

/admin/users
/admin/audit-logs
/admin/system-status

/conversations
/knowledge-bases
/knowledge-bases/{kb_id}/files
/ingestion-jobs
/mcp-connections
```

Swagger 文档应声明 Bearer 认证，并将公开与私有接口明确分组。

## 6. 对话隔离

### 6.1 创建会话

服务端从认证上下文写入 `owner_id`。客户端可以提供会话名称和聊天类型，但不能指定所有者。

### 6.2 查询历史

读取消息前先在同一查询中验证：

```text
conversation.id = 请求会话 ID
AND conversation.owner_id = 当前用户 ID
AND conversation.deleted_at IS NULL
```

消息写入、反馈、重命名、清空和删除遵守同一条件。

### 6.3 Chat Completions

- `conversation_id` 只表示当前用户范围内的会话；
- 找不到或不属于当前用户时返回统一资源不存在；
- 流式后台任务必须复制受验证的 `Principal`，不能在后台重新相信请求体；
- 消息保存、Agent 中间步骤和反馈记录都继承同一个 `user_id`；
- 服务端生成 `message_id` 或验证客户端提供的 ID 未被其他用户占用。

## 7. 知识库、文件和向量隔离

### 7.1 数据库范围

知识库、文件和文档片段的所有 CRUD 必须从当前用户开始查询。不能先按全局 `kb_name` 找到知识库，再补充权限检查。

### 7.2 磁盘范围

建议目录：

```text
data/
  users/
    {user_id}/
      knowledge_bases/
        {kb_id}/
          content/
          vector_store/
      temp_uploads/
        {upload_id}/
      media/
        {media_id}/
```

规则：

- 路径由服务端的 UUID 组成，不直接拼接用户名、知识库显示名和原始文件名；
- 原始文件名只作为元数据展示；
- 所有最终路径必须解析并校验仍位于当前用户根目录；
- 防止 `..`、绝对路径、符号链接和同名覆盖；
- 临时文件设置过期时间并由后台任务清理。

### 7.3 向量库范围

- FAISS：每个用户的每个知识库使用独立目录和锁；
- 支持 metadata filter 的远程向量库：每条记录写入 `owner_id`、`kb_id`、`file_id`，查询必须附带过滤；
- 不支持可靠服务端过滤的向量后端：使用独立 collection/index，不能查询后再在应用层过滤；
- 删除用户或知识库时，数据库、文件目录和向量集合使用可恢复任务统一处理。

### 7.4 私有下载

停止通过 `/media/{path}` 直接公开私有文件。改为：

```text
GET /files/{file_id}/download
GET /media/{media_id}
```

服务端验证当前用户后流式返回文件。若未来使用对象存储，可以在授权后生成短时有效的签名 URL。

## 8. MCP、密钥和工具隔离

### 8.1 MCP 所有权

- 每个连接器归属于一个用户；
- 不同用户可以使用同一个 `server_name`；
- 列表、启用、禁用、更新和删除都按 `owner_id` 过滤；
- 连接器健康状态只向所有者返回。

### 8.2 敏感信息

- `env`、Authorization Header、访问令牌等敏感字段加密存储；
- 列表和详情接口返回掩码，不返回原值；
- 编辑表单为空表示保持原值，明确操作才删除凭据；
- 日志、异常、审计 metadata 和模型上下文统一执行敏感字段脱敏；
- 主加密密钥来自部署 secret，不写入仓库或数据库。

### 8.3 工具执行

- ToolContext 必须包含服务端 Principal；
- 知识库工具只列出和检索当前用户知识库；
- 文件工具只能访问当前用户沙箱目录；
- Shell 默认关闭，开启后也不能继承整个宿主机环境变量；
- 外部写操作要求用户确认，并将确认人、参数摘要和结果写入审计日志；
- 模型生成的 `user_id`、路径或知识库名称不能覆盖服务端授权上下文。

## 9. 用户管理界面

### 9.1 普通用户

用户菜单提供：

- 当前用户名和角色；
- 修改密码；
- 管理个人 API Key；
- 查看和撤销其他登录会话；
- 退出登录。

知识库、会话、上传任务和连接器列表只显示自己的资源，不需要在页面增加“用户筛选”来掩盖后端未隔离的问题。

### 9.2 管理员

管理员页面提供：

- 创建用户；
- 启用或禁用用户；
- 设置角色；
- 重置密码并生成一次性临时密码；
- 撤销用户会话和 API Key；
- 查看账户状态、最近登录时间和审计事件。

第一轮管理员默认不提供浏览用户聊天正文和知识库文档的入口。若后续确有合规或支持需求，应设计显式授权、操作理由和完整审计。

## 10. 数据迁移方案

### 10.1 先引入迁移工具

当前项目主要使用 `Base.metadata.create_all/drop_all` 和知识库迁移脚本，无法安全表达用户表新增、外键、唯一约束变化和字段回填。用户体系实施前应引入正式的版本化数据库迁移机制。

SQLite 开发环境需要使用兼容的批量表迁移方式；生产多用户部署建议 PostgreSQL。

### 10.2 迁移步骤

1. 停止写入，记录数据库、文件和向量索引数量；
2. 备份数据库、知识库目录、媒体目录和配置；
3. 创建 `legacy-admin` 管理员，由部署者设置新密码；
4. 新增允许为空的 owner/稳定 ID 字段；
5. 将现有会话、消息、知识库、文件、片段、MCP 配置归属 `legacy-admin`；
6. 为每个知识库生成稳定 `kb_id`，建立旧名称到新 ID 映射；
7. 将磁盘目录移动或复制到新的用户隔离路径，并校验文件数和哈希；
8. 更新向量索引路径或 collection metadata；
9. 验证记录数、文件数、向量条目数和抽样检索结果；
10. 将 owner 字段改为非空并创建新唯一约束；
11. 启动新版本，只读验证后恢复写入；
12. 在约定观察期后再清理旧目录。

迁移不得调用会重建或删除用户数据的 `chatchat kb -r` 作为替代方案。

### 10.3 回滚

- 数据库使用迁移前备份恢复；
- 新文件路径在验证完成前保留旧目录；
- 向量索引复制验证后再切换配置；
- 迁移脚本支持 dry-run，只输出计划和冲突；
- 对名称冲突、缺失文件、孤立消息和孤立向量记录生成报告，不静默丢弃。

## 11. 安全要求

- 登录接口限速，并记录不含密码的失败事件；
- 访问令牌短期有效，刷新会话可撤销；
- API Key 只在创建时显示一次；
- 修改密码、禁用用户和重置密码后按策略撤销会话；
- Cookie 方案必须处理 `HttpOnly`、`Secure`、`SameSite` 和 CSRF；
- CORS 使用明确允许列表，不能在带凭据时使用 `*`；
- 资源 ID 使用不可预测 UUID，但仍必须做授权；
- 文件上传限制大小、类型、数量，并对归档解压和路径穿越进行防护；
- 不在日志中记录问题正文、回答正文、文档正文、密码、令牌和 MCP 凭据；
- 静态资源与私有用户文件使用不同目录和不同访问方式。

## 12. 测试矩阵

至少创建 `admin`、`user_a`、`user_b` 三个测试账户。

### 12.1 认证测试

- 正确登录、错误密码、禁用账户、过期会话；
- 刷新、退出、会话撤销、密码修改后的失效；
- API Key 创建、调用、过期和撤销；
- 公开接口可以匿名访问，私有接口不能匿名访问。

### 12.2 越权测试

用户 A 尝试访问用户 B 的：

- 会话列表、会话详情、消息历史和反馈接口；
- 知识库列表、检索、上传、下载、编辑、删除和重建；
- 临时文件知识库和媒体文件；
- 上传任务及错误详情；
- MCP 列表、配置、启停和删除；
- Agent 工具中的知识库、文件和连接器。

测试必须覆盖 GET、POST、PUT、DELETE、流式 SSE、后台任务和 OpenAI 兼容接口，不能只测普通 REST 读取。

### 12.3 存储测试

- 同名知识库和同名文件在不同用户下互不影响；
- 向量检索不会返回其他用户片段；
- 删除一个用户资源不会删除另一个用户的同名资源；
- 恶意文件名不能逃逸用户目录；
- 私有媒体链接不能绕过鉴权；
- 并发创建、上传、删除时仍保持所有权一致。

### 12.4 管理测试

- 普通用户不能调用管理员接口；
- 管理员可以管理账户，但默认不能通过普通业务接口读取其他用户内容；
- 禁用账户后已有流式请求和后台任务按明确策略取消或停止持久化；
- 敏感操作产生完整且脱敏的审计记录。

## 13. 后续扩展边界

第一轮完成后，如果出现共享知识库和团队协作需求，再增加：

```text
workspace
workspace_member
resource_acl 或 knowledge_base_member
```

届时所有权从 `owner_id` 扩展为个人所有或 workspace 所有。扩展仍应遵守默认私有、服务端授权和向量过滤不能遗漏的原则，不应通过给管理员或所有登录用户开放全库查询来实现“共享”。
