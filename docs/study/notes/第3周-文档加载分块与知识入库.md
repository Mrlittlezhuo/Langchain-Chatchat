# 第 3 周：文档加载、分块与知识入库

## 1. 本周结论

本周已完成，学习时间截止到 `2026-09-03`。

本周完整追踪了一份原始文件如何经过 Loader、TextSplitter 和 Embedding，最终变成 FAISS 向量和 SQLite 管理记录。同时用同一份文档对比了三组分块参数，并使用 BGE-M3 和内存 FAISS 验证了召回效果。

核心结论：

1. Loader 负责把不同格式的原始文件转换为 LangChain `Document`；
2. TextSplitter 负责将较长的 `Document` 切成适合检索和模型上下文的 Chunk；
3. `chunk_size` 是最大目标，`chunk_overlap` 是尽量保留的上限，实际重叠不一定等于配置值；
4. BGE-M3 将每个 Chunk 转换为 1024 维向量；
5. `index.faiss` 保存数值向量，`index.pkl` 保存 Document 和 ID 映射；
6. `knowledge_file` 保存原始文件管理信息，`file_doc` 保存文件与 FAISS Document UUID 的关系；
7. 对当前《大模型推理优化策略.md》和三个测试问题，`750/150` 是三组参数中最均衡的选择，但不是所有文档的通用最优值。

## 6. PDF 文字提取与 OCR

源码位置：

```text
chatchat/server/file_rag/document_loaders/mypdfloader.py:13-96
```

`RapidOCRPDFLoader` 不是对所有页面无条件整页 OCR，而是：

```text
每页先调用 page.get_text("") 提取原生文字层
  ↓
枚举页面中带有 xref 的内嵌图片
  ↓
计算图片宽高占页面的比例
  ↓
宽度和高度都达到 PDF_OCR_THRESHOLD 才 OCR
  ↓
合并文字层和 OCR 文字
  ↓
partition_text() 转为 Unstructured 元素
```

当前阈值是 `(0.6, 0.6)`，因此图片的宽度和高度都必须至少占页面 60%。小 Logo、图标和装饰图通常被跳过；扫描 PDF 的整页图通常会进入 OCR。

## 7. `ChineseRecursiveTextSplitter`

### 7.1 分隔符优先级

源码位置：

```text
chatchat/server/file_rag/text_splitter/chinese_recursive_text_splitter.py:32-94
```

默认从粗到细尝试：

```text
\n\n
\n
。！？
.、!、?
；
，
```

算法先用当前文本中能匹配的最粗分隔符切分，如果小段仍超过 `chunk_size`，就使用后续更细的分隔符递归切分。

### 7.2 为什么实际 Chunk 不等长

`chunk_size` 是合并上限，不是固定切片长度。为保留换行、句子和列表项的完整性，当加入下一个小段会超过上限时，当前 Chunk 会提前结束。

### 7.3 Overlap 的真实语义

LangChain `_merge_splits()` 保留的是完整小分段，不是机械复制前一块最后 N 个字符。它会从旧 Chunk 头部不断删除完整小段，尽量使剩余长度不超过 `chunk_overlap`。

因此：

- 可保留的完整小段合计 114 字符时，实际重叠就是 114，不是 150；
- 最后一个不可继续切分的小段本身超过重叠上限时，可能全部移除，实际重叠为 0；
- `strip()` 和连续换行压缩也会影响严格字符匹配统计。

Overlap 太小会破坏跨 Chunk 的语义连续性；太大会产生重复向量、挤占 Top K 和 LLM 上下文，降低召回结果的多样性。

## 8. Embedding 与 FAISS 写入

源码位置：

```text
chatchat/server/knowledge_base/kb_service/base.py:117-154
chatchat/server/knowledge_base/kb_service/faiss_kb_service.py:81-96
```

`KBService.add_doc()` 是通用流程：检查 Embedding 模型、取得文档块、规范化 `metadata["source"]`，再通过动态分派调用 FAISS 的 `do_add_doc()`。

真正的向量化位置：

```python
texts = [doc.page_content for doc in docs]
metadatas = [doc.metadata for doc in docs]
embeddings = vs.embeddings.embed_documents(texts)
ids = vs.add_embeddings(
    text_embeddings=zip(texts, embeddings),
    metadatas=metadatas,
)
```

输入 N 个 Chunk 时，BGE-M3 返回 N 个 1024 维向量。`add_embeddings()` 把数值向量写入 FAISS Index，把文本和 metadata 写入 Docstore，并为每个 Document 生成 UUID。

`not_refresh_vs_cache=True` 只表示暂时不将内存索引保存到磁盘，不表示不更新内存 FAISS。批量更新完成后由上层统一保存。

## 9. FAISS 缓存的必要边界

源码位置：

```text
chatchat/server/knowledge_base/kb_cache/faiss_cache.py:90-142
chatchat/server/knowledge_base/kb_cache/base.py:15-86
```

本周只保留与入库直接相关的结论：

- 缓存键是 `(kb_name, vector_name)`，同一知识库使用不同 Embedding 时不共享索引；
- 首次访问时从 `index.faiss/index.pkl` 加载，后续请求复用内存对象；
- `threading.Event` 防止其他线程取到未初始化完成的 FAISS；
- `RLock` 保护同一 FAISS 对象的加载、查询和更新；
- `with acquire() as vs` 在进入代码块前加锁，在正常或异常退出时都会释放锁。

缓存淘汰、锁竞争和异常恢复不属于第 3 周主线，不再深入。

## 10. FAISS、SQLite 和原始文件的数据分布

### 10.1 数据保存位置

| 数据 | 保存位置 |
|---|---|
| 原始文件本体 | `knowledge_base/<kb>/content/` |
| Chunk 数值向量 | `index.faiss` |
| Chunk `page_content` | `index.pkl` 的 Docstore |
| Chunk metadata | `index.pkl`，同时复制到 `file_doc.meta_data` |
| FAISS Document UUID | `index.pkl` 的 ID 映射，同时复制到 `file_doc.doc_id` |
| 原始文件管理信息 | SQLite `knowledge_file` |
| 文件与 Chunk UUID 关系 | SQLite `file_doc` |

检索时，FAISS 先找到数值索引位置，再通过 `index_to_docstore_id` 找到 UUID，最后从 Docstore 返回 `Document(page_content, metadata)`。SQLite 主要用于文件管理，不参与 FAISS 的底层距离计算。

### 10.2 ORM 模型

源码位置：

```text
chatchat/server/db/models/knowledge_file_model.py:6-39
chatchat/server/db/repository/knowledge_file_repository.py:69-158
chatchat/server/db/session.py:9-35
```

`KnowledgeFileModel` 一个原始文件一条，记录文件名、扩展名、Loader、TextSplitter、修改时间、大小、Chunk 数和是否自定义 docs。

`FileDocModel` 一个 Chunk 一条，记录 `kb_name`、`file_name`、`doc_id` 和 `meta_data`。其中表主键 `id` 是 SQLite 自增整数，`doc_id` 才是 FAISS/LangChain 生成的 UUID。

### 11.5 召回对比

|---|---|---|---|
| A | Top 1 完整，Top 3 纯度高 | 需要合并 Top 1/2 | 需要合并 Top 1/2 |

## 12. 为什么更换 Embedding 必须重建向量库

不同 Embedding 模型可能产生不同维度，比如当前 BGE-M3 产生 1024 维向量。新旧维度不同时，FAISS 无法在同一索引中比较。

即使两个模型恰好输出相同维度，它们学习到的坐标含义也不同，旧文档向量与新查询向量不处于同一语义空间，距离没有可比性。

因此必须使用新模型对所有 Chunk 重新 Embedding，并重建 FAISS 索引。

## 13. 验收问题与答案

### 13.1 为什么不直接对整份长文档 Embedding

长文档包含多个主题，压缩为一个固定维度向量后会产生语义稀释，降低局部问题的召回精度。即使整篇被召回，也会占用大量 LLM 上下文并引入无关内容。过长输入还可能超过 Embedding 模型的输入限制而被截断或报错。

### 13.2 Overlap 太小和太大的影响

Overlap 太小可能把尚未结束的语义切到两块，检索时只召回其中一块，导致证据不足。Overlap 太大会让相邻向量过度相似，重复结果挤占 Top K 和 LLM 上下文，并增加 Embedding 和存储成本。

### 13.3 正文、向量、metadata 和 ID 保存在哪里

`index.faiss` 保存数值向量；`index.pkl` 保存 Chunk 正文、metadata 以及 FAISS 位置到 Document UUID 的映射；`knowledge_file` 保存原始文件管理信息；`file_doc` 保存文件与 Document UUID 的关系并复制 metadata；原始文件本体保存在 `content/`。

### 13.4 为什么更换 Embedding 后需要重建

新旧模型可能输出不同维度；即使维度相同，不同模型学到的语义坐标含义也不同。只有文档向量与查询向量由同一模型生成，距离才有意义。

## 14. 已观察到但未纳入缺陷清单的点

以下内容是源码学习中的记录，尚未获得确认，因此没有写入 `项目缺陷与优化清单.md`：

1. `update_doc()` 与 `add_doc()` 存在重复删除，第二次删除未传递 `not_refresh_vs_cache`；
2. FAISS 初始化失败后，未完成的占位缓存可能使后续线程持续等待；
3. `add_file_to_db()` 与 `add_docs_to_db()` 使用独立 Session，文件记录和 Chunk 映射缺少统一事务；
4. `with_session` 与 `session_scope` 都执行 commit/rollback，职责重复；
5. `knowledge_file/file_doc` 缺少外键和唯一约束，数据一致性主要依赖应用层；
6. PDF Loader 会提前初始化 OCR，可能重复合并文字层和图片 OCR 文字，且没有保留页码 metadata。

这些内容需要后续逐条确定严重度和修复范围，得到用户同意后才能进入正式缺陷清单。
