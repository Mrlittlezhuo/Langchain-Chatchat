# 知识库检索阈值语义不一致问题

> 项目：Langchain-Chatchat  
> 项目版本：`0.3.1.3`  
> LangChain 版本：`0.1.17`  
> 向量库：FAISS  
> 检索方式：BM25 + FAISS + RRF  
> Embedding：BGE-M3  
> 问题定位日期：2026-08-21

## 1. 问题摘要

Langchain-Chatchat 的知识库配置将默认检索阈值设置为：

```yaml
SCORE_THRESHOLD: 2.0
```

项目接口注释将该参数解释为：

```text
分数越小，相关度越高；设置为 2 相当于不筛选。
```

但是，当前项目实际调用的 LangChain `similarity_score_threshold` 使用的是另一套语义：

```text
相关度范围为 0～1；
分数越大，相关度越高；
过滤条件为 similarity >= score_threshold。
```

因此，当阈值为 `2.0` 或 `1.5` 时，FAISS 语义检索分支不可能返回任何正常结果。

这个问题没有直接表现为“知识库搜索为空”，因为项目同时启用了 BM25 关键词检索。即使 FAISS 被全部过滤，BM25 仍然可以返回文档，导致系统表面可用、实际退化为以关键词检索为主。

本次在学习环境中将默认阈值暂时调整为：

```yaml
SCORE_THRESHOLD: 0.4
```

并通过直接读取 FAISS 真实相关度、重启 API、读取 OpenAPI 运行态默认值和重新检索四个步骤完成验证。

## 2. 问题影响

### 2.1 直接影响

默认配置下，FAISS 分支可能完全没有结果：

```text
用户问题
  ├── BM25 → 正常返回
  └── FAISS → 所有结果被 threshold=2.0 过滤
```

最终 Ensemble Retriever 仍能返回 BM25 结果，因此接口不会明显报错。

### 2.2 业务影响

当用户问题包含原文关键词时，BM25 可能仍然表现良好。例如：

```text
大模型推理优化有哪些常见策略？
```

示例文档中本来就有“大模型”“推理”“优化”等词，BM25 可以找到正确文件。

但在以下场景中，系统容易出现召回下降：

- 用户使用同义表达，原文没有相同关键词；
- 用户问题比较口语化；
- 专有名词存在缩写、别名或中英文差异；
- 需要根据整句语义而不是单个词进行匹配；
- 关键词密度较低，但语义高度相关。

### 2.3 隐蔽性

这个问题比直接报错更危险，因为：

1. API 返回 HTTP 200；
2. 接口确实返回三个文档；
3. 三个文档看起来与问题相关；
4. 系统没有明确提示 FAISS 分支为空；
5. API 返回的 `score` 又不是真实分数。

如果只验证“页面能回答问题”，很容易误认为混合检索工作正常。

## 4. 最初发现问题的现象

调用接口：

```bash
curl -sS \
  -X POST \
  http://127.0.0.1:7861/knowledge_base/search_docs \
  -H 'Content-Type: application/json' \
  -d '{
    "query": "大模型推理优化有哪些常见策略？",
    "knowledge_base_name": "samples",
    "top_k": 3,
    "score_threshold": 1.5,
    "file_name": "",
    "metadata": {}
  }'
```

接口返回了三个与“大模型推理优化”相关的文档块。

但出现两个反常现象：

1. 请求阈值为 `1.5`，结果仍然存在；
2. 三条结果的 `score` 全部为 `3.0`。

如果按照接口注释理解，`1.5` 属于比较宽松的距离阈值，返回结果似乎合理。但如果按照 LangChain 当前的相关度语义理解，`1.5` 已经超出最大值 `1.0`，FAISS 不应返回任何结果。

这构成了进一步追踪源码的起点。

## 5. 第一层分析：从 API 路由追踪参数

接口入口位于：

```text
chatchat/server/knowledge_base/kb_doc_api.py
```

核心参数定义：

```python
score_threshold: float = Body(
    Settings.kb_settings.SCORE_THRESHOLD,
    description="知识库匹配相关度阈值，取值范围在0-1之间，"
                "SCORE越小，相关度越高，"
                "取到2相当于不筛选，建议设置在0.5左右",
    ge=0.0,
    le=2.0,
)
```

这里本身已经存在矛盾：

```text
文字说取值范围是 0～1；
参数校验却允许最大值 2；
文字又说越小越相关；
同时把 2 描述为不过滤。
```

API 随后调用：

```python
docs = kb.search_docs(query, top_k, score_threshold)
```

API 层没有自己计算相似度，而是继续把阈值传给知识库 Service。

## 6. 第二层分析：知识库 Service 没有转换阈值

公共 Service 位于：

```text
chatchat/server/knowledge_base/kb_service/base.py
```

核心逻辑：

```python
def search_docs(self, query, top_k, score_threshold):
    if not self.check_embed_model()[0]:
        return []

    docs = self.do_search(query, top_k, score_threshold)
    return docs
```

这一层只完成两件事：

1. 检查 Embedding 模型是否存在；
2. 把原始阈值直接传给具体向量库实现。

它没有执行：

- 距离到相关度的转换；
- `2.0` 到“不过滤”的特殊映射；
- 阈值方向反转；
- 阈值范围修正。

因此 API 传入的 `1.5` 或配置中的 `2.0` 会原样进入 FAISS Retriever。

## 7. 第三层分析：FAISS 实际使用 Ensemble Retriever

FAISS Service 位于：

```text
chatchat/server/knowledge_base/kb_service/faiss_kb_service.py
```

核心逻辑：

```python
def do_search(self, query, top_k, score_threshold):
    with self.load_vector_store().acquire() as vs:
        retriever = get_Retriever("ensemble").from_vectorstore(
            vs,
            top_k=top_k,
            score_threshold=score_threshold,
        )
        docs = retriever.get_relevant_documents(query)
    return docs
```

这说明当前 FAISS 知识库不是只做向量检索，而是创建了一个 `ensemble` 混合检索器。

## 8. 第四层分析：阈值只作用于 FAISS，不作用于 BM25

Ensemble 实现位于：

```text
chatchat/server/file_rag/retrievers/ensemble.py
```

FAISS Retriever：

```python
faiss_retriever = vectorstore.as_retriever(
    search_type="similarity_score_threshold",
    search_kwargs={
        "score_threshold": score_threshold,
        "k": top_k,
    },
)
```

BM25 Retriever：

```python
docs = list(vectorstore.docstore._dict.values())

bm25_retriever = BM25Retriever.from_documents(
    docs,
    preprocess_func=jieba.lcut_for_search,
)

bm25_retriever.k = top_k
```

融合：

```python
ensemble_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, faiss_retriever],
    weights=[0.5, 0.5],
)
```

关键结论：

```text
score_threshold 只传给 faiss_retriever；
bm25_retriever 没有使用该阈值。
```

因此，即使 FAISS 返回空列表，BM25 仍然返回最多 `top_k` 个结果。

## 9. 第五层分析：确认 LangChain 的真实阈值语义

项目依赖的是已安装在环境中的 LangChain 0.1.17。仅阅读项目注释不够，因此使用：

```python
inspect.getsource(
    VectorStore.similarity_search_with_relevance_scores
)
```

查看当前运行环境真正执行的依赖源码。

LangChain 的方法说明：

```text
Return docs and relevance scores in the range [0, 1].
0 is dissimilar, 1 is most similar.
```

过滤实现：

```python
docs_and_similarities = [
    (doc, similarity)
    for doc, similarity in docs_and_similarities
    if similarity >= score_threshold
]
```

由此得到确定结论：

| 阈值 | 当前 LangChain 中的实际效果 |
|---:|---|
| `0.0` | 基本不过滤正常的 0～1 相关度 |
| `0.4` | 保留相关度大于等于 0.4 的结果 |
| `0.5` | 保留相关度大于等于 0.5 的结果 |
| `1.0` | 只保留相关度等于 1 的极端结果 |
| `1.5` | 不可能有正常结果 |
| `2.0` | 不可能有正常结果 |

项目默认值 `2.0` 与底层实现完全不兼容。

## 10. 为什么接口仍然返回了三个结果

调用流程可以还原为：

```text
query = 大模型推理优化有哪些常见策略？

BM25 分支
  ├── jieba 分词
  ├── 命中“大模型、推理、优化”等关键词
  └── 返回三个文档

FAISS 分支
  ├── BGE-M3 生成查询向量
  ├── 计算归一化相关度
  ├── similarity >= 1.5
  └── 没有任何结果

Ensemble
  ├── BM25 有结果
  ├── FAISS 为空
  └── 最终仍返回 BM25 的三个结果
```

因此，接口返回文档不能证明 FAISS 正常工作。

## 11. 为什么返回的 `score` 全部是 `3.0`

这是与阈值问题同时暴露出的关联问题，但不是阈值失效的根因。

响应模型位于：

```text
chatchat/server/knowledge_base/model/kb_document_model.py
```

定义：

```python
class DocumentWithVSId(Document):
    id: str = None
    score: float = 3.0
```

API 当前转换代码：

```python
data = [
    DocumentWithVSId(
        **{"id": x.metadata.get("id"), **x.dict()}
    )
    for x in docs
]
```

这里没有向 `DocumentWithVSId` 传入真实分数，所以响应模型自动使用默认值：

```text
score = 3.0
```

因此：

```text
API 中的 score=3.0 不是 FAISS 距离；
不是归一化相关度；
不是 BM25 分数；
也不是 RRF 分数。
```

它只是没有传值时的模型默认值，不能用于分析检索质量。

## 12. 混合检索的融合方式

LangChain `EnsembleRetriever` 使用 Weighted Reciprocal Rank Fusion，即加权倒数排名融合。

公式：

```text
RRF(document) = Σ weightᵢ / (rankᵢ + c)
```

当前参数：

```text
BM25 权重：0.5
FAISS 权重：0.5
c：60
rank：从 1 开始
```

例如，某文档在 BM25 和 FAISS 中都是第一名：

```text
BM25 贡献 = 0.5 / (1 + 60)
FAISS 贡献 = 0.5 / (1 + 60)
最终贡献   ≈ 0.01639
```

如果 FAISS 因阈值错误而为空，同一个文档只能获得 BM25 一路贡献。

RRF 分数只用于内部排序，没有附加到最终 `Document`，这也是 API 无法输出真实融合分数的原因之一。

## 16. 为什么 `0.4` 只是临时基线

当前实验只有一个查询和一个小型示例知识库，不能据此认定 `0.4` 是生产环境最优值。

阈值会受到以下因素影响：

- Embedding 模型；
- 文档语言；
- 文档领域；
- `CHUNK_SIZE`；
- `OVERLAP_SIZE`；
- 查询长度；
- FAISS 距离策略和归一化函数；
- 是否存在 Reranker；
- `top_k`；
- 人工标注的相关性标准。

正确做法是准备评测集，例如：

```text
查询
期望命中的文件
期望命中的文档块
是否允许部分相关
是否属于无答案问题
```

然后评估：

- Recall@K；
- Precision@K；
- MRR；
- nDCG；
- 无答案问题误召回率；
- 最终回答忠实度。

5. Retriever 结果模型；
6. 单元测试和接口测试。

参数可以设计为：

```python
score_threshold: float = Body(
    0.4,
    description=(
        "归一化相关度阈值，范围 0～1，"
```

### 19.2 STAR 版本

**Situation**  
知识库搜索能够返回相关文档，但三条结果的分数全部为 3.0，项目默认阈值为 2.0。

**Task**  
确认系统是否真正使用 FAISS 语义检索，并判断分数和阈值的真实含义。

从 `/knowledge_base/search_docs` 追踪到 KB Service、FAISS Service 和 Ensemble Retriever；发现阈值只传给 FAISS。随后用 `inspect` 查看运行环境中的 LangChain 源码，确认相关度范围为 0～1且过滤方向为 `>=`。最后绕过 Ensemble 直接获取五条 FAISS 真实分数，证明默认 2.0 会过滤全部结果。同时定位到 API 的 3.0 只是响应模型默认值。

**Result**  
将学习环境阈值修改为 0.4，不重建向量库，只重启 API。通过 OpenAPI 看到运行态默认值变为 0.4，最小请求返回三条正确文档。问题从“页面看似能用”转化为有源码、实验和运行态证据支持的完整结论。

## 20. 面试追问

### 20.1 为什么接口有结果，FAISS 却可能没有结果？

因为使用了 BM25 和 FAISS 两路检索。阈值只传给 FAISS，BM25 仍然可以返回结果，RRF 可以基于单路结果继续输出。

### 20.2 为什么不能相信 API 返回的 `score=3.0`？

响应模型把 `score` 默认写成 3.0，API 转换时没有传入真实分数，因此它不是任何检索算法的实际得分。

### 20.3 为什么不把阈值直接设置为 0？

0 基本等于不过滤，可以最大化召回，但也可能引入大量无关内容。当前用 0.4 是基于样例分数的实验基线，最终应由评测集决定。

### 20.4 为什么修改阈值后不用重建 FAISS？

阈值发生在查询阶段，不参与文本切块、Embedding 或索引构建。只需让 API 进程重新加载配置。

### 20.5 为什么要查看依赖库源码？

项目注释和当前依赖行为发生了语义漂移。只有查看运行环境真正安装的 LangChain 实现，才能确认实际过滤方向和分数范围。

### 20.6 生产环境应该如何防止类似问题？

- 锁定依赖版本；
- 为参数语义建立契约测试；
- 记录每路 Retriever 的返回数量和分数；
- 对依赖升级执行检索回归评测；
- 不用无含义的默认分数掩盖数据缺失。

## 21. 最终结论

本问题不是 FAISS、BGE-M3 或知识库索引损坏，而是一次跨层参数语义不一致：

```text
配置层和 API 注释
仍使用旧距离语义
        │
        ▼
Service 不做转换
        │
        ▼
LangChain Retriever
使用新相关度语义
        │
        ▼
FAISS 结果被全部过滤
        │
        ▼
BM25 掩盖故障
```

本次处理恢复了学习环境中的 FAISS 分支，但完整工程修复仍应同步更新默认配置、API Schema、检索结果模型、可观测性和回归测试。
