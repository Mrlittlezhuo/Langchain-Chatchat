## 4. 案例一：Poetry 配置检查失败

### 4.1 现象

项目存在 `pyproject.toml`，但没有 `poetry.lock`。执行：

```bash
poetry check
```

出现大量错误，例如：

```text
Cannot find dependency "ollama" for extra "ollama"
Cannot find dependency "aleph-alpha-client" for extra "extended-testing"
```

同时出现 Poetry 旧格式弃用警告。

### 4.2 分析

`[tool.poetry.extras]` 中声明了：

```toml
ollama = ["ollama"]
extended_testing = ["大量包名"]
```

但这些包没有全部出现在 `[tool.poetry.dependencies]` 中。Poetry 2.4.1 的检查比项目编写时使用的旧版本更加严格。

这不是“本地少安装了几个包”，而是项目包元数据不一致。直接执行 `poetry lock` 可能重算并改写整个依赖图，不适合作为第一反应。

### 4.3 处理

查看官方开发部署指南后，使用它提供的另一条源码安装路径：

```bash
python -m pip install -e .
```

`-e` 表示 editable install。环境中的安装记录直接指向当前源码目录，修改 Python 源码后通常无需重新安装。

### 4.4 验证

```bash
python -m pip show langchain-chatchat
which chatchat
```

验证结果：

```text
Version: 0.3.1.3
Editable project location: .../libs/chatchat-server
.../envs/Langchain-Chatchat/bin/chatchat
```

### 4.5 面试表达

不要说“Poetry 坏了，所以换 Pip”。更准确的表达是：

> 我先用 `poetry check` 做静态元数据检查，发现 extras 引用了未声明依赖，同时仓库没有 lock 文件。为了避免在尚未理解依赖图时重写锁文件，我采用项目官方同时支持的 editable Pip 安装路径，把上游包配置缺陷与本地开发环境搭建解耦。

## 5. 案例二：Python 3.11 与旧版 Pandas 不兼容

### 5.1 现象

首次使用 Python 3.11.15 安装时失败：

```text
Collecting pandas<1.4.0,>=1.3.0
Using cached pandas-1.3.5.tar.gz
Getting requirements to build wheel ... error
ModuleNotFoundError: No module named 'pkg_resources'
```

### 5.2 关键证据

最重要的证据不是最后一行 `pkg_resources`，而是：

```text
pandas-1.3.5.tar.gz
```

如果存在适配当前 Python 的预编译包，Pip 应下载 `.whl`。下载 `.tar.gz` 说明没有 CPython 3.11 对应 wheel，Pip 被迫走旧版 Pandas 源码构建路径。

### 5.3 根因

项目虽然声明：

```toml
python = ">=3.10,<3.12"
```

但同时固定：

```toml
pandas = "~1.3.0"
```

这两个约束在 Python 3.11 上的实际可安装性并不好。`pkg_resources` 只是源码构建阶段暴露出的第一层错误；即使补装或降级 Setuptools，后面仍可能遇到旧 Pandas 与 Python 3.11 C API 的兼容问题。

### 5.4 处理

没有直接修改项目依赖，也没有在原地堆叠构建补丁，而是先预览 Conda 变更：

```bash
conda install python=3.10 --dry-run
```

Dry Run 显示只需要切换 Python、Packaging、Setuptools 和 Wheel 的 Python 构建版本。随后执行：

```bash
conda install python=3.10
```

最终环境为 Python 3.10.20。

### 5.5 验证

```bash
python --version
python -m pip --version
poetry env info
python -m pip install -e .
```

验证结果：

- Python、Pip、Poetry 均指向同一个 Conda 环境；
- Pandas 1.3.5 使用 CPython 3.10 wheel，不再源码构建；
- `langchain-chatchat-0.3.1.3` 安装成功。

### 5.6 面试表达

> 我没有被最后一行缺少 `pkg_resources` 误导，而是向上寻找第一个发生策略变化的位置，发现 Pip 因 CPython 3.11 没有 Pandas 1.3.5 wheel 而退回源码构建。结合项目依赖年代，我通过 Conda Dry Run 评估影响后切换到 Python 3.10，使依赖解析回到预编译 wheel 路径。

## 6. 案例三：Requests 依赖版本警告

### 6.1 现象

执行 CLI 或 Python 请求时出现：

```text
RequestsDependencyWarning:
urllib3 (2.7.0) or chardet (7.6.0)/charset_normalizer (3.5.1)
doesn't match a supported version
```

### 6.2 分析

逐项检查后：

- `urllib3 2.7.0` 仍在 Requests 的 `<3` 范围；
- `charset_normalizer 3.5.1` 仍在 `<4` 范围；
- `chardet 7.6.0` 超出 Requests 支持的 `<6` 范围。

`chardet` 由 `unstructured` 使用，不能不分析依赖关系就直接删除。

### 6.3 处理

先 Dry Run：

```bash
python -m pip install --dry-run "chardet>=3.0.2,<6"
```

确认只会安装 Chardet 5.2.0 后执行：

```bash
python -m pip install "chardet>=3.0.2,<6"
```

### 6.4 验证

```bash
python -m pip show chardet
python -c 'import requests; print(requests.__version__)'
```

结果：Requests 2.32.5 无警告导入，`unstructured` 对 Chardet 的依赖仍然满足。

## 7. 案例四：Wheel 与 Packaging 冲突的风险取舍

### 7.1 现象

```bash
python -m pip check
```

报告：

```text
wheel 0.47.0 requires packaging>=24.0,
but packaging 23.2 is installed
```

### 7.2 分析

旧版 LangChain 依赖链使用 Packaging 23.x，而 Conda 提供的新 Wheel 要求 Packaging 24+。强行升级 Packaging 会把冲突转移给旧 LangChain；降级到很旧的 Wheel 又可能引入已披露安全风险。

Wheel 是构建工具，不是 Chatchat 请求处理链路中的运行时组件。当前应用已经完成 editable 安装，因此该冲突没有阻塞运行。

### 7.3 处理状态

没有为了让 `pip check` 变绿而盲目改版本。本问题记录为环境技术债，等待后续通过以下方式之一统一解决：

1. 使用项目验证过的锁文件和包管理器版本；
2. 升级完整 LangChain 依赖栈并做回归测试；
3. 将构建工具隔离到独立构建环境。

### 7.4 面试表达

> 并非所有警告都应立即通过改版本消除。我先判断它是否位于运行路径、修改是否会扩散、替代版本是否有安全风险。该冲突只涉及构建工具，应用运行验证通过，因此我选择记录技术债，而不是把旧 LangChain 环境改成未知组合。

## 8. 案例五：`CHATCHAT_ROOT` 在新终端中丢失

### 8.1 现象

执行配置备份时：

```text
cp: 对 '/model_settings.yaml' 调用 stat 失败
```

### 8.2 根因

`CHATCHAT_ROOT` 通过：

```bash
export CHATCHAT_ROOT=...
```

设置后只对当前 Shell 及其子进程有效。切换到新终端后变量为空：

```text
"$CHATCHAT_ROOT/model_settings.yaml"
→ "/model_settings.yaml"
```

### 8.3 处理

重新导出并在任何写操作前验证：

```bash
export CHATCHAT_ROOT=/home/lab239/chenzhuo/chatchat-study-data
printf 'CHATCHAT_ROOT=<%s>\n' "$CHATCHAT_ROOT"
test -f "$CHATCHAT_ROOT/model_settings.yaml"
```

### 8.4 验证

使用 `cmp` 验证配置备份与原文件逐字节一致。

### 8.5 后续改进

可以在专用 Conda 环境的激活脚本中设置该变量，避免污染所有 Shell；不要急于把项目专用变量全局写入 `.bashrc`。

## 11. 案例八：远程开发环境的监听地址

### 11.1 问题

如果把服务绑定为：

```yaml
host: 127.0.0.1
```

只有服务器本机可以访问。开发者通过另一台电脑连接远程服务器时，本地浏览器无法直接打开页面，除非使用 SSH 端口转发。

### 11.2 实际网络

```text
服务器地址：10.10.12.248/23
UFW：inactive
Ollama：127.0.0.1:11434
Chatchat API：0.0.0.0:7861
WebUI：0.0.0.0:8501
```

### 11.3 处理

保留 API 和 WebUI 的 `0.0.0.0` 监听，同时设置：

```yaml
API_SERVER:
  host: 0.0.0.0
  port: 7861
  public_host: 10.10.12.248
  public_port: 7861
```

Ollama 仍只监听回环地址，避免模型服务直接暴露到局域网。

### 11.4 验证

```text
服务器 curl /docs → HTTP 200
OpenAPI 标题 → Langchain-Chatchat API Server
OpenAPI 版本 → 0.3.1.3
注册接口数量 → 48
本地浏览器 → 可以打开 http://10.10.12.248:7861/docs
```

### 11.5 安全边界

`0.0.0.0` 不是安全措施，只是监听范围。UFW 未启用时，任何能路由到服务器的主机都可能访问 API。实验数据中不应保存敏感文档或真实密钥；正式部署需要防火墙、反向代理、TLS 和认证。

## 13. 案例十：默认检索阈值让 FAISS 分支失效

这是本次最适合面试展开的问题。

### 13.1 现象

知识库搜索接口使用：

```json
{
  "query": "大模型推理优化有哪些常见策略？",
  "top_k": 3,
  "score_threshold": 1.5
}
```

返回三个相关结果，但所有 `score` 都是 `3.0`。项目默认配置甚至是：

```yaml
SCORE_THRESHOLD: 2.0
```

### 13.2 第一层源码证据

API 注释写着：

```text
SCORE 越小，相关度越高
2 相当于不筛选
```

但 FAISS Service 实际创建：

```python
vectorstore.as_retriever(
    search_type="similarity_score_threshold",
    search_kwargs={"score_threshold": score_threshold, "k": top_k},
)
```

### 13.3 第二层依赖源码证据

通过 `inspect.getsource()` 查看当前 LangChain 0.1.17 的实际实现，确认：

```text
相关度范围：[0, 1]
0 最不相关，1 最相关
过滤条件：similarity >= score_threshold
```

所以：

```text
threshold=1.5 → FAISS 不可能有结果
threshold=2.0 → FAISS 不可能有结果
```

接口返回的结果来自不受该阈值影响的 BM25 分支。

### 13.4 直接绕过 Ensemble 验证

直接调用 FAISS `similarity_search_with_relevance_scores()`，得到：

| 排名 | 真实相关度 | 来源 | 人工判断 |
|---:|---:|---|---|
| 1 | 0.6283 | 大模型推理优化策略.md | 相关 |
| 2 | 0.4811 | 大模型推理优化策略.md | 相关 |
| 3 | 0.4707 | 大模型应用技术原理.md | 部分偏题 |
| 4 | 0.4236 | 大模型推理优化策略.md | 相关 |
| 5 | 0.4225 | 大模型应用技术原理.md | 部分偏题 |

### 13.5 处理

将学习环境默认值调整为：

```yaml
SCORE_THRESHOLD: 0.4
```

这个数值不是通用最优值，而是根据当前样例的真实得分选择的宽松基线。后续必须通过评测集调优。

### 13.6 验证

重启 API 后读取 `/openapi.json`：

```text
OpenAPI 默认 top_k：3
OpenAPI 默认 score_threshold：0.4
```

省略请求中的阈值后，返回三条来自正确文档的结果，证明运行进程加载了新配置，FAISS 分支也具备参与融合的条件。

### 13.7 根因分类

这是一次典型的依赖升级语义迁移问题：

```text
旧实现：原始距离，越小越相关，2 近似不过滤
新实现：归一化相关度，越大越相关，范围 0～1
```

业务配置、接口注释和参数校验没有随底层 Retriever 语义一起更新。

## 14. 案例十一：API `score=3.0` 是假分数

### 14.1 现象

`/knowledge_base/search_docs` 的三个结果都返回：

```json
"score": 3.0
```

### 14.2 源码证据

响应模型：

```python
class DocumentWithVSId(Document):
    id: str = None
    score: float = 3.0
```

API 当前转换代码：

```python
DocumentWithVSId(
    **{"id": x.metadata.get("id"), **x.dict()}
)
```

它没有传入 `score`，因此 Pydantic 自动使用默认值 `3.0`。

同一文件中还保留了被注释的旧代码：

```python
# score=x[1]
```

说明项目从 `(Document, score)` 返回结构迁移到 Ensemble 的 `Document` 列表后，API 契约没有完成同步。

### 14.3 处理状态

本次没有直接取消注释旧代码，因为当前 `docs` 元素已经不是元组，直接恢复会产生运行错误。

当前规避方式：

1. 不使用 API 中的 `score=3.0` 做相关性判断；
2. 调试时直接调用 FAISS 获取真实 relevance score；
3. 使用来源、正文和人工评测判断融合结果。

### 14.4 正确修复方向

建议定义明确的检索结果模型，例如：

```python
class RetrievalResult(BaseModel):
    document: Document
    retriever: str
    raw_score: float | None
    relevance_score: float | None
    fusion_score: float | None
    rank: int
```

Ensemble 在融合时保留每路分数和 RRF 分数，API 不应使用无含义的魔法默认值。

## 15. 案例十二：混合检索实现与扩展性风险

### 15.1 实际实现

```python
faiss_retriever = vectorstore.as_retriever(...)

docs = list(vectorstore.docstore._dict.values())
bm25_retriever = BM25Retriever.from_documents(
    docs,
    preprocess_func=jieba.lcut_for_search,
)

EnsembleRetriever(
    retrievers=[bm25_retriever, faiss_retriever],
    weights=[0.5, 0.5],
)
```

### 15.2 RRF 算法

LangChain 使用 Weighted Reciprocal Rank Fusion：

```text
RRF(document) = Σ weightᵢ / (rankᵢ + c)
```

当前：

```text
BM25 权重：0.5
FAISS 权重：0.5
c：60
rank 从 1 开始
```

同一正文被两路命中时分数累加，最终按 RRF 分数降序排列。去重键是完整的 `page_content`，因此内容重叠但不完全相同的相邻块仍会同时出现。

### 15.3 风险

1. 每次查询重新从全部 docstore 构建 BM25；
2. 使用 `vectorstore.docstore._dict` 私有属性；
3. 755 个块影响不明显，大型知识库会增加请求时延；
4. RRF 分数没有附加到结果，API 可观测性不足；
5. 类型注解仍写 `List[Tuple[Document, float]]`，实际返回 `List[Document]`。

### 15.4 改进方向

- 文档入库或更新时构建并缓存 BM25；
- 为不同知识库维护版本号，文件变化时使缓存失效；
- 避免访问第三方类私有属性；
- 为 Retriever 定义统一结果协议；
- 在日志中记录各分支 rank、score 和最终 fusion rank；
- 增加大规模知识库的性能基准测试。

## 19. 高频追问与回答要点

### 19.1 为什么不直接升级 Pandas？

项目固定了旧版 LangChain 及相关依赖。单独升级 Pandas 会创建未经验证的依赖组合；切换到项目约束实际更匹配的 Python 3.10，变更范围更小，也更容易复现。

### 19.2 为什么阈值选 0.4？

它不是通用最优值，而是根据当前样例真实相关度分布选出的宽松基线。正式项目应准备带相关性标注的查询集，通过召回率、MRR、nDCG 和答案质量共同调优。

### 19.3 BM25 和向量检索为什么要组合？

BM25 擅长精确关键词、专有名词和编号；向量检索擅长同义表达和语义召回。RRF 使用排名而不是直接混合不可比的原始分数，降低了分数尺度不同的问题。

### 19.4 如何证明模型真的使用 GPU？

不能只看驱动存在。需要同时验证 Ollama 日志中的 CUDA backend、`ollama ps` 的 `100% GPU`，以及 `nvidia-smi` 中模型进程和显存占用。

### 19.5 如何证明新配置被服务加载？

配置文件修改本身不是证明。需要重启进程，并从运行态读取证据。本次通过 `/openapi.json` 看到 `score_threshold` 默认值变为 0.4，再用省略阈值的请求验证。

### 19.6 为什么不直接恢复被注释的 `score=x[1]`？

旧代码假定结果是 `(Document, score)` 元组，当前 Ensemble 返回 `Document`。直接取消注释会把新的结构当成元组访问，属于错误修复。应先设计统一检索结果协议，再同步修改 Retriever、Service、API Schema 和测试。

### 19.7 `0.0.0.0` 和 `public_host` 有什么区别？

`0.0.0.0` 决定服务监听所有 IPv4 网卡；`public_host` 用于生成客户端可访问的链接。远程服务器场景可以监听 `0.0.0.0`，但必须结合防火墙、认证和网络边界控制风险。
