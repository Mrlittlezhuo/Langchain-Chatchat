## 项目介绍

### 一分钟介绍

> 我开发的是一套面向企业内部知识场景的私有知识库与 AI Agent 智能问答平台。系统以 LangChain 作为模型编排基础，后端使用 FastAPI，对接本地大语言模型和 Embedding 模型，知识检索采用 FAISS 向量召回、BM25 关键词召回与 RRF 排名融合。
>
> 平台的核心是 Agent 执行链。模型先根据用户任务和工具描述生成 AgentAction，执行器调用本地工具或 MCP 工具，再把 Observation 写入 intermediate_steps 回传模型，持续迭代直到生成 AgentFinish。执行过程通过 Callback 写入异步事件队列，再由 SSE 实时返回前端。
>
> 除了 Agent，我还完成了文档加载、中文分块、Embedding、向量索引、知识检索、多轮会话持久化、OpenAI 兼容接口和知识库 WebUI 等功能，使模型、知识、工具和业务接口形成完整闭环。

### 两分钟介绍

> 这个项目解决的是企业内部文档无法被通用模型直接、可靠使用的问题。用户既可以进行普通对话，也可以让系统检索内部知识库，或者由 Agent 自主选择知识库、搜索、计算、数据库和 MCP 等工具完成任务。
>
> 系统从架构上分为交互层、业务编排层、Agent 与 RAG 能力层、模型服务层和数据层。Streamlit 负责知识库管理与对话交互；FastAPI 提供 OpenAI 兼容的聊天接口和知识库接口；Agent 层负责模型决策、工具执行和多轮状态；RAG 层负责文档解析、分块、向量化以及混合检索；Ollama 提供本地 LLM 和 Embedding 服务；FAISS 保存向量索引与文档对象，SQLite 保存会话、消息和知识库元数据。
>
> Agent 请求进入系统后，服务端会加载会话历史、可用工具以及 MCP 连接，然后创建 AgentExecutor。模型输出工具调用意图后，OutputParser 将其解析成 AgentAction；执行器调用工具获得 Observation，并把执行轨迹加入 intermediate_steps，下一轮再交给模型判断。模型给出 AgentFinish 后，系统保存最终回答和工具轨迹。与此同时，模型 Token、工具开始、工具结束和 Agent 完成事件通过 Callback 与异步队列实时推送到前端。
>
> RAG 方面，文档上传后依次经过 Loader、中文 TextSplitter、Embedding 和 FAISS 索引构建，文件信息与向量文档映射保存在 SQLite。查询时同时使用 FAISS 和 BM25 召回，通过 RRF 融合后拼装知识上下文，再交给模型生成回答。整个项目覆盖了 Agent、RAG、模型接入、异步接口、状态管理和数据持久化等 AI 应用开发的主要环节。

### 一次 Agent 请求的主链路

```text
用户提交消息和工具配置
→ FastAPI 校验 OpenAI 风格请求
→ 加载模型、会话历史、本地工具和 MCP 连接
→ 创建 AgentExecutor
→ 模型生成 AgentAction
→ OutputParser 解析工具名和参数

→ 下一轮模型继续决策
→ 模型生成 AgentFinish
→ 保存回答和工具轨迹
→ 通过 SSE 返回执行状态与最终答案
```

## 项目整体问题

### 问题：这个项目解决了什么业务问题？

**建议回答：**

> 通用模型不了解企业内部文档，而且单纯把全部资料放入 Prompt 会受到上下文长度、成本和噪声影响。这个项目通过 RAG 按问题检索相关知识，通过 Agent 在需要时选择知识库、搜索、计算或数据库工具，从而让模型既能使用私有数据，也能执行外部动作。系统同时提供本地模型接入和数据本地存储，适用于对数据隐私有要求的内部知识问答场景。

### 问题：为什么不仅做 RAG，还要加入 Agent？

**建议回答：**

> RAG 的核心是“先检索再生成”，适合回答知识库中的事实问题，但它不能自然覆盖计算、实时搜索、数据库查询和跨系统操作。Agent 增加了一层动态决策：模型可以根据任务选择工具、生成参数、读取工具结果并决定下一步。因此，RAG 是 Agent 可以调用的一类知识工具，Agent 则负责更上层的任务编排。

### 问题：这个项目最核心的技术难点是什么？

**建议回答：**

> 最核心的难点不是调用一次模型，而是让模型决策、工具执行、状态回传和最终回答形成稳定闭环。模型输出是不确定的，但工具参数、API Schema 和数据库状态要求确定性，所以系统需要 OutputParser、参数校验、执行边界、超时控制和错误处理。同时，Agent 主循环与前端流式状态是两条并行链，既要保证后台任务继续执行，也要让用户实时看到过程。

### 问题：你在项目中负责哪些内容？

**建议回答：**

> 我负责 Agent 执行链、工具管理、Prompt 上下文、多轮会话、RAG 文档与检索链路、模型接入、FastAPI 接口、SSE 流式交互以及知识库页面等模块的开发，并完成这些模块之间的数据结构和调用关系设计。我的重点是让模型、工具、知识和业务状态形成一套可运行、可追踪的完整系统。

## Agent 执行引擎

### 问题：你如何定义这个项目中的 Agent？

**建议回答：**

> Agent 不是一次普通的模型调用，而是一个受执行器控制的多轮决策过程。模型负责根据用户输入、工具描述和已有 Observation 决定下一步；OutputParser 把模型输出转换成结构化动作；Executor 负责真正调用工具并保存结果；当模型输出 AgentFinish，或者达到迭代与时间限制时，任务结束。

### 问题：请详细说明 Agent 的一次执行流程。

**建议回答：**

> 请求进入聊天接口后，服务端先提取用户最后一条消息、会话标识、工具配置和 MCP 开关，再创建模型对象并加载历史消息。随后根据工具列表创建 AgentExecutor。执行器调用 agent.aplan，让模型产生 AgentAction 或 AgentFinish。如果得到 AgentAction，执行器按照工具名找到可执行工具，传入 tool_input，得到 Observation，并把二者组成 AgentStep 加入 intermediate_steps。下一轮会将这些步骤格式化为 agent_scratchpad 再交给模型。模型认为任务完成时返回 AgentFinish，系统保存最终回答和执行轨迹。

### 问题：谁负责决定调用哪个工具，谁负责真正执行工具？

**建议回答：**

> 模型负责生成调用意图，但模型不会直接执行代码。模型输出经过 OutputParser 后形成 AgentAction，其中包含工具名和参数；PlatformToolsAgentExecutor 根据工具名从注册表或 MCP 工具集合中找到真正的工具对象，再执行同步或异步调用。因此模型决策与工具执行是分离的。

### 问题：AgentAction、AgentStep 和 AgentFinish 分别是什么？

**建议回答：**

> AgentAction 表示模型决定执行某个工具，包含工具名、工具参数和模型输出日志；AgentStep 表示动作已经执行完成，由 AgentAction 和 Observation 组成；AgentFinish 表示模型不再需要工具，已经形成最终回答。三者对应“准备执行”“执行完成”和“任务结束”三个阶段。

### 问题：intermediate_steps 有什么作用？

**建议回答：**

> intermediate_steps 保存已完成的 AgentAction 与 Observation，是 Agent 的工作状态。每次工具执行后，新的步骤都会追加进去；下一轮模型调用前，系统把这些步骤格式化成 agent_scratchpad，使模型知道自己调用过哪些工具、参数是什么、返回了什么。没有这个状态，模型会重复执行相同工具，或者无法基于工具结果继续推理。

### 问题：chat_history 和 intermediate_steps 有什么区别？

**建议回答：**

> chat_history 是用户与助手跨轮次的自然语言对话历史，主要提供会话语义；intermediate_steps 是 Agent 在执行当前或历史任务时产生的工具轨迹，包含动作和 Observation。前者回答“之前聊过什么”，后者回答“为了完成任务已经做过什么”。两种状态用途不同，不能简单拼成同一段文本。

### 问题：Agent 如何支持多步推理？

**建议回答：**

> Executor 使用循环控制执行过程。每一轮模型根据用户输入和已有 intermediate_steps 产生下一步动作，工具结果回到 intermediate_steps 后再次进入模型。只要模型仍返回 AgentAction，循环就继续；当模型返回 AgentFinish，或者触发迭代次数和执行时间限制时结束。多步能力来自“决策—执行—观察—再决策”的闭环，而不是一次生成很长的思维文本。

### 问题：模型一次输出多个工具调用时如何处理？

**建议回答：**

> 输出解析器可以返回多个 AgentAction，执行器将每个动作转成 AgentStep，并统一加入 intermediate_steps。是否并发执行取决于执行器实现和工具之间的依赖关系。对于无依赖的只读工具可以并发以降低延迟；对于写操作或前后依赖明显的工具，应顺序执行，避免状态竞争和参数依赖错误。

### 问题：Agent 在什么情况下结束？

**建议回答：**

> 正常情况下，模型输出 AgentFinish 后结束。如果工具配置了直接返回，也可以在工具执行后提前结束。异常情况下，执行器还会受到最大迭代次数、最大执行时间、工具异常和请求取消的约束。这样可以防止模型反复调用工具形成无限循环。

### 问题：如果模型生成了不存在的工具名怎么办？

**建议回答：**

> 执行器不会直接按模型输出动态执行任意代码，而是只允许从已注册工具映射中查找。找不到工具时，通过 InvalidTool 生成结构化 Observation，告诉模型请求的工具无效以及当前可用工具。下一轮模型可以重新选择；同时服务端记录异常轨迹，便于分析是 Prompt、工具描述还是模型能力导致的问题。

### 问题：如果模型输出的工具参数格式不正确怎么办？

**建议回答：**

> 第一层由 OutputParser 把模型输出解析成结构化参数；第二层由工具的 Pydantic Schema 做类型、必填字段和取值范围校验；第三层由工具实现捕获业务异常并返回明确错误。对于可恢复错误，可以把错误作为 Observation 回传模型，让模型修正参数；对于权限、危险操作或不可恢复错误，应直接终止并返回安全错误信息。

### 问题：Agent 为什么需要 OutputParser？

**建议回答：**

> 模型返回的是消息或文本，而执行器需要确定的 AgentAction 或 AgentFinish。OutputParser 是不确定生成与确定性程序之间的边界，它负责识别工具调用标签、解析工具名和参数、区分最终回答，并在解析失败时提供降级行为。没有这一层，业务代码就需要到处处理模型格式差异。

### 问题：模型的“思考”是否等于 Agent 的执行过程？

**建议回答：**

> 不等于。模型生成的 thinking 或文本只是模型输出的一部分；真正可验证的执行过程是 AgentAction、工具调用、Observation 和 AgentFinish。工程上更应该记录结构化动作和工具结果，而不是依赖不可控的自然语言思考内容。

### 问题：为什么自己控制 AgentExecutor，而不是只使用简单 Chain？

**建议回答：**

> 简单 Chain 更适合固定步骤，输入经过确定的组件后直接得到输出。Agent 的步骤由模型动态决定，需要处理多轮工具调用、无效工具、工具直返、超时和执行轨迹，因此必须由 Executor 维护循环和状态。自定义执行器也便于把本地工具、平台工具和 MCP 工具统一到同一执行模型中。

## 工具管理与 MCP

### 问题：统一工具管理机制是如何实现的？

**建议回答：**

> 本地工具通过注册器维护，注册时保存工具名称、描述、参数 Schema 和执行函数。请求选择工具后，服务端从注册表取得 BaseTool 对象，一份工具描述交给模型用于决策，另一份可执行对象交给 Executor 用于真实调用。这样工具发现、模型理解和程序执行相互解耦。

### 问题：工具 Schema 和可执行工具对象为什么要分开？

**建议回答：**

> Schema 面向模型，告诉模型工具叫什么、能做什么、需要哪些参数；可执行对象面向服务端，包含真正的 Python 调用逻辑、回调、超时和异常处理。模型只能看到允许暴露的能力描述，不能直接获得任意函数执行权限，这也是工具调用安全边界的一部分。

### 问题：如何新增一个本地工具？

**建议回答：**

> 我会先定义清晰的工具名称和职责，再用 Pydantic 定义输入 Schema，明确必填字段、类型和约束；然后实现同步或异步执行函数，并通过注册装饰器加入工具注册表。测试分三层：直接调用工具验证业务逻辑，通过 Agent 验证工具选择和参数生成，最后通过 API 验证状态事件和最终回答。

### 问题：为什么工具描述非常重要？

**建议回答：**

> Agent 选择工具主要依赖名称、描述和参数定义。描述过于相似会导致工具路由混淆，描述缺少边界会让模型在不适用的场景调用工具，参数说明不完整则容易产生空值或错误格式。因此工具描述需要包含用途、适用条件、不适用条件和关键参数要求。

### 问题：什么是 MCP？项目为什么支持 MCP？

**建议回答：**

> MCP 是模型应用连接外部工具和资源的一套标准协议。项目支持 MCP 后，Agent 不需要为每个外部系统编写强耦合适配代码，而是通过 MCP Client 连接不同 Server，发现工具 Schema，再包装成统一的 MCPStructuredTool。Executor 仍按 AgentAction 执行工具，因此 MCP 工具与本地工具可以共享 Agent 主循环。

### 问题：本地工具和 MCP 工具有何区别？

**建议回答：**

> 本地工具与应用运行在同一 Python 进程或同一服务环境，调用路径短，但依赖和权限与主应用耦合。MCP 工具由独立 Server 提供，可以使用 stdio 或 SSE 等传输方式连接，隔离性和扩展性更好，但需要处理连接生命周期、网络超时、服务发现和远端错误。

### 问题：MCP 工具是如何进入 Agent 的？

**建议回答：**

> 服务端先根据启用的连接配置创建 MultiServerMCPClient，与各 MCP Server 建立会话并获取工具列表。客户端把远端工具转换为 MCPStructuredTool，其中保存 server_name、工具 Schema 和调用逻辑。创建 AgentExecutor 时，本地工具和 MCP 工具同时传入；模型产生 MCPToolAction 后，执行器根据 server_name 与工具名定位远端工具并调用。

### 问题：为什么 MCPToolAction 还需要 server_name？

**建议回答：**

> 不同 MCP Server 可能暴露同名工具，仅凭工具名无法唯一定位。server_name 与 tool name 组成实际的路由键，可以避免调用到错误服务，也便于权限、日志和超时按 Server 维度管理。

### 问题：如何保障工具调用安全？

**建议回答：**

> 首先使用工具白名单，Executor 只能调用已注册或已连接的工具；其次使用 Schema 校验参数，不接受任意代码或未声明字段；对文件、Shell、数据库写入等高风险工具增加最小权限、路径限制和人工确认；同时设置超时、输出大小限制、敏感信息脱敏和审计日志。来自知识库和工具返回的文本都应视为不可信数据，不能覆盖系统指令。

### 问题：工具调用失败后应该重试吗？

**建议回答：**

> 不能统一重试。网络超时、限流等瞬时错误可以使用带退避的有限重试；参数错误应把校验信息回传模型后重新生成参数；数据库写入、发送消息等有副作用的工具必须先设计幂等键，避免重试造成重复操作；权限错误和危险请求不应自动重试。

## Prompt 与上下文管理

### 问题：Agent Prompt 中包含哪些信息？

**建议回答：**

> Prompt 包括系统角色与行为约束、当前时间和工作目录等运行环境、可用本地工具、可用 MCP 工具、历史消息、用户当前请求以及由 intermediate_steps 生成的 agent_scratchpad。不同信息需要明确分区，避免模型把环境描述当成用户任务，或者把工具返回内容当成更高优先级指令。

### 问题：为什么要把环境信息和用户请求显式隔离？

**建议回答：**

> 如果直接把工作目录、时间和用户请求拼成一段文本，小参数模型可能错误判断真正任务，例如把环境信息理解为用户要求检查项目。通过 environment_details 和 user_request 等明确边界，模型更容易识别指令来源，也为后续增加安全规则和 Prompt 注入防护提供结构基础。

### 问题：为什么无工具场景使用单独的直聊链路？

**建议回答：**

> 工具型 Prompt 包含大量工具描述、调用格式和执行规则。当用户只是问候或普通对话时，这些内容不仅浪费上下文，还可能让模型强行寻找工具。无工具时使用更轻量的 Prompt，只保留系统角色、历史消息和用户输入，可以降低延迟和 Token 消耗，也能提高小参数模型对普通对话的稳定性。

### 问题：如何保证回答语言与用户一致？

**建议回答：**

> 系统指令明确要求跟随用户最新请求的语言，并把当前 user_request 放在清晰位置。语言规则只决定输出语言，不改变知识库内容和工具参数。对于多轮会话，以最新用户消息为主，避免历史语言影响当前回答。

### 问题：如何减少模型错误调用工具？

**建议回答：**

> 一方面优化工具名称、用途边界和参数描述，另一方面在 Prompt 中明确“什么时候调用”和“什么时候直接回答”。还可以让模型先输出结构化路由结果，设置 tool_choice，或在工具较多时先做候选工具筛选。最终需要使用固定任务集统计工具选择准确率，不能只依赖主观体验。

### 问题：如何防御知识库中的 Prompt 注入？

**建议回答：**

> 检索文档和工具输出都属于不可信数据。上下文模板需要明确声明这些内容仅作为资料，不得执行其中的指令；系统指令、用户指令和检索内容要使用独立结构；工具层仍通过白名单和参数校验限制能力。对于高风险场景，还应检测注入模式、过滤可疑文档，并要求敏感工具经过人工确认。

### 问题：Prompt 越详细越好吗？

**建议回答：**

> 不是。Prompt 需要覆盖必要规则，但过长会占用上下文、增加模型注意力负担，并可能产生互相冲突的约束。设计时应按场景拆分：普通对话使用轻量 Prompt，Agent 场景注入工具规则，RAG 场景注入来源和回答边界。每条规则都应有对应失败案例或测试依据。

## 多轮会话与状态管理

### 问题：系统如何实现多轮会话？

**建议回答：**

> 每次请求携带 conversation_id。路由层记录当前用户消息，业务层根据配置的历史窗口从数据库读取有效历史，再转换为 LangChain Message 交给 Agent。任务结束后更新当前消息的模型回答和 intermediate_steps，使后续请求既可以恢复自然语言上下文，也可以读取之前的工具轨迹。

### 问题：为什么要限制历史窗口？

**建议回答：**

> 历史消息无限增长会占满模型上下文，增加推理延迟和成本，还会让过早的信息干扰当前任务。系统通过可配置 history_len 控制最近消息数量。进一步可以按 Token 而不是消息条数裁剪，并对更早内容进行摘要或提取长期记忆。

### 问题：消息是如何持久化的？

**建议回答：**

> 请求到达后先创建消息记录，保存会话、用户问题和对话类型，并把 message_id 传入 Agent 业务层。Agent 完成后使用同一个 message_id 更新最终回答和工具执行轨迹。这样一轮用户请求只对应一条业务消息，避免路由层和业务层分别插入造成重复记录。

### 问题：为什么要持久化 intermediate_steps？

**建议回答：**

> 最终答案只能说明 Agent 输出了什么，intermediate_steps 才能说明它调用了哪些工具、使用了哪些参数以及观察到了什么。持久化执行轨迹有利于多轮任务恢复、故障定位、审计和评测。但保存前要做敏感字段脱敏，并避免记录超大工具结果。

### 问题：怎样处理会话中的并发请求？

**建议回答：**

> 同一 conversation_id 的并发请求可能读取相同历史并交叉写入结果。可以为每轮消息生成独立 message_id，增加创建时间或序列号，并在会话级使用乐观锁、版本号或任务队列保证顺序。工具执行状态也应绑定 run_id，不能只依赖 conversation_id。

### 问题：短期记忆和长期记忆怎么设计？

**建议回答：**

> 短期记忆是当前会话最近消息和本次 intermediate_steps，直接进入模型上下文；长期记忆可以把历史事实、用户偏好或任务结果结构化存储，需要时通过检索召回。长期记忆不能把所有历史原文持续追加，否则会造成上下文膨胀和隐私风险。

## RAG 文档处理链路

### 问题：请说明文档从上传到可检索的完整过程。

**建议回答：**

> 上传接口先校验知识库和文件名，再把原文件保存到知识库目录。KnowledgeFile 根据扩展名选择 Loader，将文件转换成 LangChain Document；TextSplitter 按中文标点和段落结构切分文本；Embedding 模型把每个 Chunk 转换为向量；FAISS 保存向量索引、正文和 metadata；SQLite 保存知识库、文件信息以及文件与向量文档 ID 的映射。全部完成后，查询才能通过向量或关键词召回对应 Chunk。

### 问题：系统如何支持多种文档格式？

**建议回答：**

> KnowledgeFile 根据文件扩展名选择对应 Loader，不同 Loader 统一输出 LangChain Document。上层分块、Embedding 和索引逻辑只依赖 Document 的 page_content 与 metadata，因此不需要关心原文件是 PDF、Word、PPT、Markdown 还是文本。这是通过统一中间数据模型隔离格式差异。

### 问题：为什么不能把整篇文档直接做 Embedding？

**建议回答：**

> 长文档通常包含多个主题，压缩成单个向量会造成语义稀释，局部问题不容易召回；整篇放入模型上下文也会引入大量无关信息，增加成本并可能超过输入限制。分块可以让检索定位到更细的证据单元，但块太小又会破坏上下文，因此需要在主题纯度和证据完整性之间平衡。

### 问题：chunk_size 和 chunk_overlap 分别有什么作用？

**建议回答：**

> chunk_size 控制单个文本块的最大长度，影响语义聚焦程度和上下文成本；chunk_overlap 让相邻块保留部分共同内容，减少关键句在边界被截断的问题。Overlap 太小可能丢失跨块语义，太大则会产生重复向量、占用 Top K 并浪费模型上下文。

### 问题：中文文本分块与英文有什么差异？

**建议回答：**

> 中文没有天然空格分词，句子边界更多依赖换行、句号、问号、分号和其他中英文标点。中文递归分块器会按从强到弱的分隔符逐层切分，并重新合并小片段。实际 Chunk 长度和 overlap 通常不是严格固定值，因为算法优先保留完整语义片段。

### 问题：Embedding 模型和生成模型有什么区别？

**建议回答：**

> Embedding 模型把文本映射成固定维度向量，用于语义距离计算；生成模型根据 Prompt 和上下文逐 Token 生成回答。文档和问题必须使用同一 Embedding 模型及同一向量空间，否则相似度没有意义。生成模型则负责理解检索结果并组织最终答案。

### 问题：更换 Embedding 模型后为什么要重建索引？

**建议回答：**

> 不同 Embedding 模型可能输出不同维度，即使维度相同，向量坐标的语义也不同。旧模型生成的文档向量不能与新模型生成的查询向量直接比较，因此必须重新计算所有文档向量并重建 FAISS 索引。

### 问题：FAISS 中保存了什么？

**建议回答：**

> FAISS 的数值索引文件保存向量和近邻搜索结构；Docstore 保存 Chunk 正文和 metadata；索引位置通过映射关联到 Document ID。SQLite 另外保存文件管理信息和 Document ID 映射。也就是说，向量、正文和业务元数据并不全部位于同一存储中。

### 问题：为什么同时使用 FAISS 和 SQLite？

**建议回答：**

> FAISS 擅长高维向量近邻搜索，但不适合作为完整业务数据库；SQLite 负责知识库、文件、会话、消息和文档映射等结构化数据。两者职责分离后，向量检索和业务管理都更清晰，但也带来跨存储一致性问题，需要由应用层控制更新顺序和补偿逻辑。

### 问题：文档更新时如何保证数据一致性？

**建议回答：**

> 更新过程需要处理原文件、FAISS 索引、Docstore 和 SQLite 记录。理想方案是先生成新版本索引，全部成功后切换版本并更新元数据；失败时保留旧版本或执行补偿。对于大规模系统，还应使用文件哈希和版本号实现幂等，避免重试产生重复向量。

## 混合检索与答案生成

### 问题：知识库查询的完整链路是什么？

**建议回答：**

> 用户问题进入知识库聊天接口后，系统根据知识库名称取得 KBService，再把查询交给 Retriever。FAISS 根据查询向量召回语义相近文档，BM25 根据分词后的关键词召回文档，RRF 使用两路排名进行融合。最终文档正文被拼入 RAG Prompt，与用户问题一起交给生成模型，答案和来源再返回客户端。

### 问题：为什么要同时使用 FAISS 和 BM25？

**建议回答：**

> FAISS 擅长语义相似和同义表达，但对精确编号、专有名词和罕见关键词不一定稳定；BM25 擅长词面匹配，但不能很好理解同义语义。两者结合可以提高召回覆盖率。混合检索的关键不是简单相加，而是处理不同分数尺度、噪声候选和最终质量控制。

### 问题：RRF 是什么？为什么适合融合两路检索？

**建议回答：**

> RRF 是 Reciprocal Rank Fusion。它主要根据文档在各召回列表中的名次计算融合分数，不要求 BM25 分数和向量相关度处在相同尺度。某个文档在多路检索中排名都靠前时，融合排名会提高。它实现简单、鲁棒性较好，但只看名次也意味着低质量分支可能把噪声带入结果。

### 问题：score_threshold 应该作用在哪一层？

**建议回答：**

> 向量相关度阈值只能直接作用于具有统一相关度语义的向量分支。BM25 原始分数、FAISS 相关度和 RRF 分数尺度不同，不能共用一个阈值。更完整的设计是每个召回分支使用自己的质量门槛，融合后再由 Reranker 在统一语义尺度上打分，并执行最终过滤。

### 问题：BM25 为什么容易产生噪声？

**建议回答：**

> 中文查询分词后可能包含“什么”“为什么”等低信息量词和标点，如果没有停用词处理，这些词也会参与排名；BM25 如果固定返回候选而没有最低质量门槛，即使所有文档都不相关也可能返回结果。因此需要领域停用词、最低分数或相对分数过滤，并把候选数量与最终返回数量分开。

### 问题：Reranker 在系统中应该放在哪里？

**建议回答：**

> Reranker 应放在多路召回和 RRF 初步融合之后。FAISS 与 BM25 先扩大候选范围，RRF 合并并去重，然后 Reranker 根据 query 与每个 Chunk 的联合语义重新打分，最后执行阈值过滤和 Top K 截断。这样既保留召回覆盖率，又能减少噪声进入 LLM 上下文。

### 问题：检索结果如何组织成 Prompt？

**建议回答：**

> 系统不能只把正文无结构拼接，而应为每个 Chunk 增加来源编号、文件名和必要 metadata，再将其放入明确的 context 区域。Prompt 要求模型仅基于资料回答、缺少证据时明确说明，并在关键结论后引用来源。这样可以提升可追溯性，也便于评估引用是否正确。

### 问题：没有检索到文档时怎么办？

**建议回答：**

> 应根据产品策略处理。严格知识库模式直接说明未找到依据，不允许使用模型自身知识补全；通用助手模式可以回答，但必须明确说明答案不是来自知识库。不能让空检索结果无提示地切换成自由生成，否则用户会误认为答案有企业资料支持。

### 问题：如何评估 RAG 效果？

**建议回答：**

> 需要把检索和生成分开评估。检索层关注 Recall@K、MRR、nDCG、命中文档和噪声比例；生成层关注答案正确性、完整性、忠实度和引用准确率；系统层关注首 Token 延迟、总耗时和失败率。评测集应包含事实查询、同义表达、多文档组合、无答案和对抗性问题。

## 模型接入

### 问题：为什么使用 OpenAI 兼容协议接入模型？

**建议回答：**

> OpenAI 兼容协议把上层业务与具体推理框架解耦。应用层统一使用 chat completions 和 embeddings 形式调用模型，只需要根据模型配置切换 base_url、model 和鉴权信息，就可以对接 Ollama、Xinference 或其他兼容服务。这样模型迁移不会影响 Agent 和 RAG 主链。

### 问题：系统如何根据模型名选择模型服务？

**建议回答：**

> 配置中维护模型平台、模型列表、API 地址、鉴权和并发限制。请求指定模型后，模型适配层查找该模型所属平台，创建对应的 OpenAI 同步或异步客户端，再把 LangChain Message 转换成平台请求。模型选择逻辑集中在适配层，而不是散落在各业务接口中。

### 问题：为什么把模型服务和应用服务分开？

**建议回答：**

> 模型服务负责 GPU 资源、模型加载和推理；应用服务负责会话、知识检索、Agent 编排和接口。两者资源特征和扩缩容方式不同，分开后可以独立更新模型、限制并发、监控延迟，也可以让多个业务实例共享同一模型服务。

### 问题：本地模型方案有什么优缺点？

**建议回答：**

> 优点是数据不离开本地环境、模型和日志可控、没有外部 API 依赖；缺点是需要承担 GPU 资源、模型服务稳定性、并发和版本管理。小参数模型在工具选择和复杂 JSON 输出方面也更容易出错，因此更依赖清晰 Prompt、Schema 校验和失败重试。

### 问题：模型并发如何控制？

**建议回答：**

> 可以按模型平台设置 Semaphore，限制同时进入推理服务的请求数，防止 GPU 显存不足或队列失控。不同模型的生成和 Embedding 请求可以使用独立并发限制，并记录等待时间、推理时间和超时。大规模部署时应由模型网关提供排队、限流和负载均衡。

## FastAPI 与 OpenAI 兼容接口

### 问题：聊天接口为什么采用 OpenAI Chat Completions 格式？

**建议回答：**

> 采用通用请求格式后，WebUI、Python SDK 和外部系统可以复用现有 OpenAI Client，不需要维护专用聊天客户端。标准字段承载 messages、model、stream 和 tools，项目自己的 conversation_id、metadata、模型配置和 MCP 开关通过 extra_body 传递。

### 问题：标准参数和业务扩展参数如何共存？

**建议回答：**

> Pydantic Schema 负责校验标准字段，同时允许保留额外字段。路由层从 model_extra 中提取项目参数，再转换为内部 chat 函数需要的 query、tool_config、conversation_id 和 use_mcp。这样对外保持协议兼容，对内仍能承载完整业务状态。

### 问题：业务聊天接口和模型网关接口有什么区别？

**建议回答：**

> 业务聊天接口负责会话、工具、Agent、知识库和消息持久化；模型网关接口主要根据模型配置选择推理平台并转发生成请求。前者是应用编排入口，后者是模型能力入口。区分两者可以避免把业务状态泄漏到纯模型层，也方便其他服务直接复用模型网关。

### 问题：FastAPI 的 async def 是否一定不会阻塞？

**建议回答：**

> 不一定。只有代码在网络 I/O 等可等待操作上 await 并让出事件循环，其他协程才能运行。PDF 解析、分块、Embedding 前处理等 CPU 或同步阻塞任务如果直接放在 async def 中，仍会阻塞事件循环，需要放入线程池、进程池或后台任务系统。

### 问题：接口层为什么不直接写 Agent 逻辑？

**建议回答：**

> 路由层只负责协议校验、参数转换和响应类型选择，Agent 层负责模型和工具编排。分层后，同一 Agent 可以被 WebUI、SDK 或其他接口复用，Agent 单元测试也不需要启动 HTTP 服务。协议变化与执行逻辑变化可以独立维护。

## SSE 流式交互

### 问题：Agent 的流式输出是如何实现的？

**建议回答：**

> AgentExecutor 在后台 asyncio Task 中执行，Callback 捕获 llm_start、llm_new_token、agent_action、tool_start、tool_end 和 agent_finish 等事件，并写入 asyncio.Queue。前台异步生成器持续消费队列，将内部事件转换成统一响应对象；流式模式下由 EventSourceResponse 通过 SSE 推送给客户端。

### 问题：为什么需要后台任务和事件队列？

**建议回答：**

> Agent 主循环负责决策和执行，HTTP 输出层负责把状态发给客户端。如果直接等待 Agent 完成，用户无法看到工具执行过程。后台任务与队列把生产者和消费者解耦：Agent 按自己的节奏产生事件，输出层按协议消费事件，而且 Agent 核心不需要依赖 Streamlit 或 SSE。

### 问题：流式和非流式请求是否有两套 Agent 逻辑？

**建议回答：**

> 没有。两种模式共用同一个异步生成器和 Agent 执行链。流式模式每取得一个事件就立即发送；非流式模式在服务端消费全部事件并聚合成最终响应。这样可以避免两套业务逻辑产生状态和错误处理差异。

### 问题：SSE 和 WebSocket 有什么区别？为什么选择 SSE？

**建议回答：**

> SSE 基于 HTTP 长连接，主要用于服务端向客户端单向推送，浏览器和代理支持简单，非常适合模型 Token 和 Agent 状态输出。WebSocket 是全双工协议，更适合客户端需要持续发送控制消息的场景。当前聊天请求是一次提交、持续接收，因此 SSE 足够；如果需要实时人工审批、暂停和恢复工具执行，可以考虑 WebSocket 或额外控制接口。

### 问题：客户端主动断开后如何处理？

**建议回答：**

> 客户端断开会导致 SSE 生成器被取消，服务端需要捕获 CancelledError，结束事件转发并尽量取消后台 Agent Task。对于已经开始的有副作用工具，不能假设取消 HTTP 就能回滚，需要单独设计任务状态、幂等和补偿机制。

### 问题：如何处理慢客户端和队列积压？

**建议回答：**

> 生产环境中队列应设置容量，低价值 Token 事件可以合并发送，关键的工具开始、结束和错误事件不能丢失。当客户端长期消费过慢时，应触发超时或取消任务。同时监控队列长度、首 Token 延迟和客户端断开率，避免无界队列造成内存增长。

## WebUI 与知识库管理

### 问题：WebUI 在系统中承担什么职责？

**建议回答：**

> WebUI 负责会话选择、模型配置、工具选择、MCP 开关、消息展示、知识库管理和来源查看。它通过 OpenAI Client 调用后端兼容接口，并根据返回事件类型分别渲染模型文本、工具状态和最终结果。业务逻辑仍位于后端，页面不直接访问向量库和数据库。

### 问题：为什么 WebUI 使用 OpenAI Client，而不是自己解析 HTTP？

**建议回答：**

> OpenAI Client 已经封装请求格式和流式响应迭代，WebUI 可以使用与外部调用方一致的客户端方式。项目特有参数通过 extra_body 传递，既减少重复客户端代码，也能验证后端接口确实具有兼容性。

### 问题：知识库管理包含哪些功能？

**建议回答：**

> 包括知识库创建与删除、文档上传与更新、向量化、文档列表、来源预览和下载，以及知识库对话。页面操作通过 API 进入统一业务层，避免页面直接修改文件或索引，便于后续接入其他客户端。

### 问题：前端如何展示 Agent 的过程状态？

**建议回答：**

> 前端根据 SSE 事件中的 message_type 和 status 区分普通 Token、AgentAction、工具开始、工具结束、错误和 AgentFinish。模型内容持续追加到回答区域，工具事件显示为独立状态块，最终完成事件结束本轮渲染。run_id 可用于关联同一次工具调用的开始和结束。

## 系统设计与工程化追问

### 问题：如果知识库规模大幅增长，当前架构会遇到什么问题？

**建议回答：**

> 单机 FAISS 的容量、并发和更新能力会成为瓶颈；每次从 Docstore 构建 BM25 会带来明显开销；SQLite 不适合高并发和多实例写入；文档解析与向量化如果在请求链中同步完成也容易超时。可以使用支持分片和 metadata 过滤的向量数据库、持久化全文索引、关系数据库以及消息队列驱动的异步入库任务。

### 问题：如何把文档入库设计成异步任务？

**建议回答：**

> 上传接口只保存文件、创建任务记录并投递消息；Worker 执行解析、分块、Embedding 和索引构建，并分阶段更新进度；前端通过 SSE 或轮询查看状态。任务使用知识库、文件哈希和版本作为幂等键，失败后有限重试，最终失败进入人工处理或死信队列。

### 问题：如何支持多租户知识库？

**建议回答：**

> 所有知识库、文档、会话、消息和工具连接都需要绑定 tenant_id，并在 API、Repository、向量检索过滤和文件路径层同时执行隔离。不能只依靠前端隐藏。MCP 凭证和模型密钥按租户加密存储，高风险工具还要结合用户角色进行授权。

### 问题：系统需要哪些可观测性？

**建议回答：**

> 每次请求使用 trace_id，Agent 任务使用 run_id，记录模型、Prompt 版本、工具名、工具耗时、错误类型、各路检索排名、最终文档、Token 用量和首 Token 延迟。Agent、检索、工具和模型层分别统计成功率与耗时，才能判断问题发生在路由、召回、执行还是生成阶段。

### 问题：如何测试这个项目？

**建议回答：**

> 工具函数和 OutputParser 做单元测试；数据库 Repository、Retriever 和模型适配层做组件测试；聊天接口、知识库接口和 SSE 事件序列做契约与集成测试；Agent 使用固定任务集评估工具选择、参数正确性、任务完成率和循环次数；RAG 单独评估检索与生成。外部模型和 MCP Server 使用可控 Stub，避免测试结果受网络和生成随机性影响。

### 问题：Agent 系统最重要的评测指标是什么？

**建议回答：**

> 不能只看最终回答是否流畅。核心指标包括任务完成率、工具选择准确率、参数正确率、无效调用率、平均步骤数、超时率和工具错误恢复率。涉及 RAG 时还要增加召回与引用指标，涉及写操作时还要评估越权率和重复执行率。

### 问题：如何降低 Agent 延迟？

**建议回答：**

> 先拆分各阶段耗时，再针对瓶颈处理：减少无关工具描述、无工具时走直聊链、限制历史上下文、缓存工具 Schema 和 BM25 索引、并发执行无依赖只读工具、使用流式输出降低感知延迟，并为模型和工具设置独立超时。不能只通过缩短 Prompt 盲目优化，因为可能降低工具选择准确率。

### 问题：如何防止 Agent 无限循环？

**建议回答：**

> Executor 设置最大迭代次数和最大执行时间；记录工具名与参数，如果连续重复相同调用且 Observation 没有变化，可以提前终止；错误 Observation 要明确告诉模型失败原因；对于复杂任务还可以维护目标状态，判断每一步是否带来进展。

### 问题：为什么没有直接把所有工具都提供给模型？

**建议回答：**

> 工具越多，Prompt 越长，名称和功能更容易相互干扰，也扩大了权限范围。系统应根据用户权限、会话场景和任务类型筛选候选工具，必要时先进行工具路由，再把少量相关工具交给 Agent。这样能同时提高准确率、安全性和推理效率。

### 问题：如果让你继续完善项目，优先做什么？

**建议回答：**

> 我会优先建立 Agent 与 RAG 的固定评测集和链路可观测性，因为没有评测就无法判断功能变化是否有效。然后完善混合检索的分支质量控制和 Reranker，补充工具超时、幂等与审批机制，最后将文档入库改成异步任务并增加多租户权限隔离。

## 故障场景题

### 问题：Agent 一直重复调用同一个工具，你怎么排查？

**建议回答：**

> 先检查工具 Observation 是否真正加入 intermediate_steps，再检查 scratchpad 是否被传入下一轮 Prompt；然后确认工具结果是否清晰到足以让模型判断任务进展；最后检查工具描述和终止规则。可以通过 run_id 对比每轮 AgentAction 与 Observation，判断是状态丢失、结果不可理解还是模型决策问题。

### 问题：模型明明输出了工具标签，但工具没有执行，可能是什么原因？

**建议回答：**

> 可能是 OutputParser 没有识别格式、工具名与注册表不一致、参数校验失败、MCP Server 未连接，或者 AgentAction 被解析成了 AgentFinish。排查时依次查看模型原始消息、Parser 输出、工具映射和 tool_start 回调，定位故障发生在哪个边界。

### 问题：工具执行成功，但前端一直显示处理中，怎么排查？

**建议回答：**

> 先确认工具是否产生 tool_end 回调，再检查 Callback 是否把事件写入 Queue，PlatformToolsRunnable 是否将事件转换为状态对象，以及 SSE 生成器是否正常 yield。如果 tool_end 已经发送但没有 agent_finish，还要检查 Observation 回灌后模型是否继续执行或陷入循环。

### 问题：知识库回答出现明显无关内容，怎么排查？

**建议回答：**

> 先跳过 LLM，直接查看 FAISS、BM25 和融合后的候选，确认问题出在召回还是生成；然后检查分词、阈值、Top K、Chunk 边界和重复文档；如果候选正确但答案错误，再检查 Prompt、上下文顺序和模型能力。RAG 排障必须先检索后生成，不能一开始就调整模型温度。

### 问题：流式接口有 Token，但最终数据库没有回答，可能是什么原因？

**建议回答：**

> Token 事件只说明模型产生了流式内容，不代表 Agent 已经正常结束。需要检查 agent_finish 是否触发、最终答案是否写入 history、更新消息时是否使用正确 message_id，以及客户端断开是否取消了持久化逻辑。持久化最好放在后台任务的 finally 或明确完成阶段，而不是依赖客户端持续连接。

### 问题：同一轮问题在数据库出现两次，如何定位？

**建议回答：**

> 从路由到 chat 业务层检查所有 add_message 调用，确认 message_id 的创建和传递边界。正确设计是由一个层创建记录并把 ID 传给后续链路，执行完成后基于同一 ID 更新，而不是每层各自创建消息。

### 问题：MCP Server 不可用时如何降级？

**建议回答：**

> 建立连接时记录 Server 状态，无法连接的工具不进入本轮可用工具列表；执行过程中断开时返回结构化错误 Observation，并根据任务类型让模型选择其他工具或结束。单个 MCP Server 故障不应阻塞所有本地工具和其他 Server，还应设置连接与调用超时。

## 高频连续追问

### Agent 主线

```text
问：谁选择工具？
答：模型生成调用意图，OutputParser 将其解析成 AgentAction。

问：谁执行工具？
答：PlatformToolsAgentExecutor 根据白名单中的工具对象执行。

问：结果如何回到模型？
答：工具结果作为 Observation 与 Action 一起进入 intermediate_steps。

问：如何形成下一轮输入？
答：intermediate_steps 被格式化为 agent_scratchpad，再与用户输入和历史交给模型。

问：什么时候结束？
答：模型返回 AgentFinish，或达到迭代、时间与错误边界。
```

### RAG 主线

```text
问：文档如何入库？
答：Loader → TextSplitter → Embedding → FAISS，同时写入文件和文档映射元数据。

问：查询如何召回？
答：FAISS 做语义召回，BM25 做关键词召回，RRF 融合排名。

问：为什么不能直接混合原始分数？
答：BM25 分数和向量相关度不在同一尺度。

问：如何控制融合后的噪声？
答：分支质量门槛、停用词、Reranker 和最终过滤。

问：如何判断回答是否可信？
答：检查检索证据、答案忠实度和引用准确率，而不是只看语言是否流畅。
```

### 流式主线

```text
问：Agent 在哪里执行？
答：在后台 asyncio Task 中执行。

问：状态从哪里产生？
答：LangChain Callback 捕获模型、动作和工具事件。

问：状态如何传递？
答：Callback 写入 asyncio.Queue，异步生成器消费并转换响应。

问：如何返回浏览器？
答：流式模式通过 EventSourceResponse 发送 SSE。

问：非流式是否重新执行？
答：不重新执行，只是在服务端聚合同一生成器产生的事件。
```

## 面试表达注意事项

### 应该强调

- 强调 Agent 是决策与执行闭环，不是普通聊天接口。
- 强调模型只生成调用意图，Executor 才真正执行工具。
- 强调 Schema、白名单、超时、幂等和权限是 Agent 的确定性边界。
- 强调 chat_history 与 intermediate_steps 的职责区别。
- 强调 RAG 的检索质量与生成质量需要分别评测。
- 强调异步任务、Callback Queue 和 SSE 是不同层次的机制。
- 回答设计问题时说明当前实现、风险以及生产化方案。

### 避免混淆

- AgentAction 不代表工具已经执行。
- tool_end 不代表整个 Agent 已结束。
- llm_end 不一定是最终回答，模型可能刚生成工具调用。
- 工具 Schema 不等于可执行工具对象。
- SSE 是输出协议，不等于异步执行本身。
- FAISS 数值索引不直接等于完整知识库数据。
- BM25、向量相关度和 RRF 分数不能直接使用同一阈值。
- `async def` 中运行同步耗时任务仍然可能阻塞事件循环。
